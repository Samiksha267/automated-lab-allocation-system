# Requirements

Requirement IDs are stable identifiers for traceability to tests (unit/integration test names should reference the FR/NFR/HC ID they cover where practical). Hard scheduling constraints (HC-01..HC-12) are specified and, as of Phase 9, fully implemented in [06-CONSTRAINTS.md](06-CONSTRAINTS.md); they are cross-referenced here.

**Status:** Requirements marked ✅ are implemented and verified. Requirements marked **(partial)** have their underlying hard-constraint logic, candidate generation, scoring, explanation, and/or alternative-suggestion logic implemented and verified but are not yet reachable through any end-user workflow. As of Phase 15, the CR-facing EXTRA-lab search/booking/cancellation workflow (`ExtraLabController`/`ExtraLabService`) is real, production-facing, and verified both by tests and live against the Dockerized stack. As of Phase 16, the booking path is additionally protected by PostgreSQL exclusion constraints and a per-division pessimistic lock, closing the concurrent-request race window Phase 15 had explicitly left open — proven live via true parallel HTTP requests, not merely reasoned about (docs/15-DESIGN-DECISIONS.md ADR-010/ADR-073). As of Phase 17, every state-changing action across CR and Lab Assistant workflows produces an immutable, append-only audit record (`audit_log`), queryable by Lab Assistants via `GET /api/audit-logs` — no frontend audit screen exists yet (Phase 20 owns Lab Assistant UI). As of Phase 18, the timetable-version lifecycle (draft → publish → automatic supersede) is fully implemented and API-reachable (`/api/schedule-versions`), students/CRs see only the current published version via `GET /api/timetable` (never a draft or superseded one), and version publication is itself an audited, atomic, concurrency-safe operation. As of Phase 19, the PDF timetable import pipeline (upload → extraction → parsing → normalization → mapping → validation → review → correction → approval) is fully implemented and API-reachable (`/api/timetable-imports`), reusing the unmodified Phase 9-14 constraint engine and the unmodified Phase 18 publication workflow — approval alone never publishes anything, verified live end-to-end.

## Functional Requirements

### Identity & Access
- **FR-01** ✅ Lab Assistant can create CR accounts. *(Phase 3: account creation via `AppUser`; Phase 4: `POST /api/cr-assignments` links an existing CR-role account to a division — "creating a CR **account**" specifically, distinct from assignment, remains the existing user-management surface, since Phase 4 explicitly used existing demo CR users rather than adding a public/admin CR-account-creation endpoint — see docs/15-DESIGN-DECISIONS.md.)*
- **FR-02** ✅ Lab Assistant can assign a CR to exactly one division, and can change/deactivate that assignment. *(`CrAssignmentService.create`/`.end`, Phase 4 — reassignment ends the prior active row and preserves it as history.)*
- **FR-03** ✅ A CR can act only within their currently assigned division; the backend resolves division from the authenticated user's identity, never from a client-supplied value. *(`CrOwnershipService.requireOwnsDivision`, Phase 4 — verified in `CrOwnershipServiceTest` and end-to-end in `AcademicApiIT`.)*
- **FR-04** Student accounts are read-only; students can never mutate scheduling data. *(Enforced generally by RBAC since Phase 3/4 — no student-mutable endpoint exists anywhere; no scheduling data exists yet to more specifically test against.)*
- **FR-05** ✅ Faculty have no login identity; they exist purely as a scheduling/domain entity maintained by the Lab Assistant. *(`Faculty` entity, Phase 4 — no `app_user` row, no password field, ADR-006.)*

### Academic Structure
- **FR-06** ✅ Lab Assistant can manage the academic hierarchy (Program, Stream, Academic Year, Division, Batch) with a configurable number of divisions per year and batches per division. *(Phase 4 — full CRUD via `/api/programs`, `/api/streams`, `/api/academic-years`, `/api/divisions`, `/api/batches`; no hardcoded counts anywhere, verified with the seeded 4-stream/4-year B.Tech + 2-stream/3-year MBA Tech hierarchy.)*
- **FR-07** ✅ Lab Assistant can manage Subjects *(Phase 4 — `/api/subjects`)* and their software/equipment/lab-type requirements *(Phase 6 — `/api/subjects/{id}/requirements`, `/software-requirements`, `/equipment-requirements`, `/lab-type-requirement`; verified with BDA requiring Cloudera + preferring the Data Engineering lab type, and CNS carrying zero requirements to prove the optional path)*. Matching these requirements against lab capabilities is now implemented and verified — `RequiredSoftwareConstraint`/`RequiredEquipmentConstraint`/`RequiredLabTypeConstraint` (HC-08/09/10, Phase 9) — but not yet reachable through any end-user workflow.
- **FR-08** ✅ Lab Assistant can manage Faculty records *(Phase 4 — `/api/faculty`)* and their weekly, term-scoped availability windows *(Phase 7 — `/api/faculty/{id}/availability*`; verified with Faculty BDA/CNS's seeded Monday/Tuesday/Wednesday windows, including a deliberate Monday 12:00-14:00 gap in BDA's schedule proving "not available" is correctly computed, not just "available"). Availability is a hard boundary (HC-03), now actually enforced by `FacultyAvailabilityConstraint` (Phase 9, verified live in Docker) — again not yet reachable through any end-user workflow.

### Lab Inventory
- **FR-09** ✅ Lab Assistant can manage Labs (code, name, capacity, wing, floor, room number, lab type, active flag). *(Phase 5 — `/api/labs`, `/api/lab-types`; verified with 15 seeded labs across wings B/C/D.)*
- **FR-10** ✅ Lab Assistant can manage Software and Equipment catalogs and which labs have which software/equipment installed. *(Phase 5 — `/api/software`, `/api/equipment`, `/api/labs/{id}/software`, `/api/labs/{id}/equipment`; static ALL-match capability filtering verified against seeded Cloudera data.)*
- **FR-11** ✅ Lab Assistant can mark a lab unavailable for a period (maintenance) via `LabUnavailability`. *(Phase 5 — `/api/labs/{id}/unavailability`; interval validation verified. Scheduling-conflict combination now implemented — `LabAvailabilityConstraint` (HC-06, Phase 9), verified live with a real unavailability window.)*

### Regular Timetable (PDF Import)
- **FR-12** ✅ Lab Assistant can upload a timetable PDF. *(Phase 19 — `POST /api/timetable-imports`, one documented pipe-delimited text format supported (docs/18-PDF-IMPORT.md); no OCR, no universal table-layout parsing — an explicit, honestly-scoped limitation, not an oversight.)*
- **FR-13** ✅ The system extracts and normalizes timetable entries from the PDF into a reviewable, editable form (`TimetableImport`/`TimetableImportRow`) — extraction never writes directly to live allocations. *(Phase 19 — verified live: staged rows exist with zero corresponding `allocation` rows until explicit approval.)*
- **FR-14** ✅ Lab Assistant must review, and may correct, every imported entry before approval. *(Phase 19 — `GET /api/timetable-imports/{id}`, `PATCH /api/timetable-imports/{id}/rows/{rowId}`, which re-validates the whole import.)*
- **FR-15** ✅ Only after Lab Assistant approval does an imported timetable become a set of real `Allocation` records; approval then requires an explicit publish step before students can see it. *(Phase 19 — `POST /api/timetable-imports/{id}/approve` creates `APPROVED` allocations inside the target `DRAFT` schedule version, atomically and revalidated against live state; Phase 18's unmodified `POST /api/schedule-versions/{id}/publish` remains the separate, required step that makes them visible. Verified live end-to-end, including the BDA/Cloudera failure-and-correction demo.)*
- **FR-16** ✅ The system detects conflicts (per HC-01..HC-12) among imported entries and against existing allocations during review, before approval is possible. *(Phase 19 — `TimetableImportValidationService` reuses the unmodified `ConstraintEngine` per row against persisted allocations, plus a dedicated cross-row pass for conflicts between rows of the same import. Verified live with the BDA/Cloudera `SOFTWARE_MISMATCH` demo and a genuine cross-import lab conflict caught at approval-time revalidation.)*

### Extra / Makeup Lab Booking (CR Workflow)
- **FR-17** ✅ A CR can search for candidate labs for a subject/batch/date/time, restricted to their own division, ranked by preference and with a structured explanation of why each ranked or was rejected. *(`POST /api/allocations/extra/search`, Phase 15 — reuses `CandidateGenerator` (Phase 10), `ScoringEngine` (Phase 11), and `ExplainableAllocationService` (Phase 12) unchanged; division is resolved server-side from the caller's `CrAssignment`, never accepted from the request body. Verified live: BDA/A1 search correctly recommends C-202 with a full score breakdown.)*
- **FR-18** ✅ The system filters candidate labs by the subject's software/equipment/lab-type requirements before further validation. *(HC-08/09/10, Phase 9, reached in production for the first time via `ExtraLabService.search`/`.book` — verified live: `C-304` correctly rejected `SOFTWARE_MISMATCH` for BDA.)*
- **FR-19** ✅ The system prevents faculty conflicts: a faculty member cannot be assigned two overlapping sessions. *(HC-02, Phase 9, now reachable in production via the Phase 15 booking workflow, with the same defense-in-depth as every other hard constraint — verified live via `ALLOCATION_CONFLICT`/`FACULTY_CONFLICT` on a real overlapping attempt.)*
- **FR-20** ✅ The system prevents lab conflicts: a lab cannot host two overlapping sessions. *(HC-01, Phase 9 — same status as FR-19; verified live via `ALLOCATION_CONFLICT`/`LAB_CONFLICT`.)*
- **FR-21** ✅ The system considers faculty availability windows; a session outside a faculty's declared availability is rejected. *(HC-03, Phase 9, reachable via Phase 15's booking workflow.)*
- **FR-22** ✅ The system distinguishes batch-level occupancy from division-wide occupancy: two different batches of the same division may have simultaneous sessions if their labs and faculty differ. *(HC-04/05, Phase 9 — the project's signature scenario, now proven through the real production booking endpoint: A1/BDA booked into C-202 and A2/CNS booked into B-201 at the identical Monday 09:00-11:00 slot, both succeeding independently.)*
- **FR-23** ✅ When a requested slot is invalid, the system provides ranked alternative allocations (different lab, different time, or both) rather than a bare rejection. *(`AlternativeSuggestionService`, Phase 13, now reached directly by `POST /api/allocations/extra/search`, which calls `findAlternatives(...)` unconditionally — the same single call resolves both the same-time recommendation and, when needed, alternative-time suggestions.)*
- **FR-24** ✅ Extra-lab requests are served First-Come-First-Served among valid requests; FCFS ordering never overrides a hard constraint. *(Phase 16 — implemented: three PostgreSQL exclusion constraints (lab/faculty/batch, `V11` migration) plus a per-division pessimistic lock (DIVISION-vs-BATCH, HC-05) make the database the final concurrency boundary, on top of Phase 15's unchanged hard-constraint revalidation. FCFS is defined precisely as commit order, not observed network arrival order (docs/15-DESIGN-DECISIONS.md ADR-073). Verified live via true parallel HTTP requests: same-lab/faculty/batch races each produce exactly one success; DIVISION-vs-BATCH races produce exactly one success in both directions; A1/A2 concurrent bookings both succeed (serialized, never rejected).)*
- **FR-25** ✅ A CR can cancel only extra allocations belonging to their own division; cancellation sets status to `CANCELLED` and records who/when/why — it never deletes the row. *(`POST /api/allocations/extra/{id}/cancel`, Phase 15 — calls the existing `Allocation.cancel(...)` lifecycle method (Phase 8) after a fresh `CrOwnershipService.requireOwnsDivision` check; verified live with real `cancelled_by`/`cancelled_at`/`cancellation_reason` values.)*
- **FR-26** ✅ A CR cannot modify, schedule, or cancel allocations for a division other than their own, even if they supply a different division ID in the request (enforced server-side). *(HC-11, Phase 9, now genuinely exercised in production: `ExtraLabService` never accepts a client-supplied `divisionId` at all — it is always resolved from the caller's own `CrAssignment` — and a batch belonging to a foreign division is independently rejected by HC-12's academic-relationship check. Verified live: a CR assigned to Division A attempting to book a foreign division's batch/subject receives `404 SUBJECT_FACULTY_ASSIGNMENT_NOT_FOUND`, never a successful booking.)*

### Viewing
- **FR-27** ✅ Student can view only the currently *published* schedule version, filterable by division/batch. *(Phase 18 — `GET /api/timetable?academicTermId=&divisionId=&batchId=`, selected by `ScheduleVersion.status = PUBLISHED`, never `MAX(version_number)` — a DRAFT/SUPERSEDED version's rows can never leak through, verified live. Filtering is by `divisionId`/`batchId` rather than the full `programId`/`streamId`/`yearId`/`divisionId`/`batchId` set — this project has no `Student` enrollment entity associating a STUDENT account with a division/batch (Phase 4 never introduced one), so filtering is client-supplied, matching the same convention CR/Lab-Assistant endpoints already use elsewhere in this project.)*
- **FR-28** ✅ CR can view their division's full schedule (regular + extra) and cancelled-session history. *(`GET /api/allocations/extra/mine`, Phase 15, covers the EXTRA half. Phase 18's `GET /api/timetable` additionally covers REGULAR sessions alongside EXTRA for the CR's own division — the previously-documented gap ("Viewing REGULAR sessions alongside them is not yet implemented") is now closed.)*
- **FR-29** *(partial)* ✅ Lab Assistant can view all schedules, all detected conflicts, suggested alternatives, and CR activity across all divisions. *(`GET /api/allocations/extra/activity`, Phase 15, covers the "CR activity" half. Phase 18 adds full timetable-version history and per-version allocation inspection (`GET /api/schedule-versions`, `GET /api/schedule-versions/{id}/allocations`) — a general all-schedules/all-conflicts admin view spanning every version at once is still not implemented.)*

### Automatic Scheduling
- **FR-30** *(partial)* ✅ The system can generate a full multi-session schedule automatically from a set of unscheduled session requirements, using most-constrained-first ordering and backtracking when a session has no valid candidate under the current partial assignment. *(`AutomaticSchedulingEngine`, Phase 14 — implemented and verified: bounded DFS backtracking with dynamic MRV ordering, reusing the unmodified Phase 9-12 pipeline for every candidate slot. Not yet reachable through any end-user workflow, and never persists a generated schedule — a future phase decides whether/how to commit one.)*
- **FR-31** *(partial)* ✅ The system reports which sessions could not be scheduled when no full solution is found within the configured search budget. *(Implemented and verified — `AutomaticScheduleResult` distinguishes `PARTIAL`/`NO_SOLUTION`/`SEARCH_LIMIT_REACHED` and reports a real, non-fabricated reason per unscheduled requirement via `ConflictAnalyzer`. Not yet reachable through any end-user workflow.)*

### Auditability
- **FR-32** ✅ The system records an immutable audit log entry for every consequential action. *(Phase 17 — implemented: `audit_log` (Flyway `V12`), append-only at both the application layer (no update/delete code path, `AuditLog` is Hibernate `@Immutable`) and the database layer (`BEFORE UPDATE OR DELETE` trigger, proven live via direct `psql`). Phase 18 added schedule-version lifecycle events; Phase 19 added `TIMETABLE_IMPORT_UPLOADED`/`TIMETABLE_IMPORT_APPROVED`/`TIMETABLE_IMPORT_REJECTED` (row corrections deliberately not individually audited, ADR-106, docs/15-DESIGN-DECISIONS.md — a considered volume decision, not an oversight).)*
- **FR-33** ✅ Lab Assistant can view CR activity and the full audit log. *(Phase 17 — `GET /api/audit-logs`, `LAB_ASSISTANT`-only, paginated (`size` capped at 100) and filterable by actor/action/resource type/term/division/date range; CR activity specifically is the `actorUserId` filter against CR-authored actions. Complementary to Phase 15's `GET /api/allocations/extra/activity` — see ADR-085, docs/15-DESIGN-DECISIONS.md.)*

### Analytics
- **FR-34** ✅ Lab Assistant can view lab utilization and scheduling analytics computed from real allocation data (never fabricated/placeholder numbers). *(Phase 23 — implemented: `GET /api/analytics/{summary,lab-utilization,unused-labs,extra-labs,peak-usage,conflicts}`, `LAB_ASSISTANT`-only, term-scoped with an optional date range. Lab utilization = booked/available minutes per lab (available minutes derived from the existing `SchedulingSlotPolicy` college working-hours config, minus overlapping `LabUnavailability`), weighted overall (never a naive average, ADR-126); extra-lab totals/breakdowns by division/subject/lab; peak day/lab/time-slot by booked minutes; unused labs (zero qualifying allocations in scope). Every query is scoped to the term's current `PUBLISHED` schedule version, excluding DRAFT/SUPERSEDED/CANCELLED rows — proven live against real multi-version historical data (docs/03-SYSTEM-ARCHITECTURE.md §31). Conflict/allocation-success metrics are honestly limited: no failed booking attempt or search-time rejection is ever persisted in this system, so `GET /api/analytics/conflicts` always reports `evidenceAvailable: false` with an explicit explanation rather than a fabricated count (ADR-127/128, docs/15-DESIGN-DECISIONS.md).)*

## Non-Functional Requirements

- **NFR-01 (Security)** All state-changing endpoints require authentication; authorization (role + ownership) is enforced server-side regardless of what the frontend sends or hides.
- **NFR-02 (Concurrency)** Two concurrent requests for the same lab/time slot must never both succeed; the database is the final arbiter, not application-level pre-checks.
- **NFR-03 (Performance)** Single-allocation candidate generation + scoring for a realistic dataset (≈15 labs) should complete fast enough for interactive use (target documented with real measurements in [16-PERFORMANCE-BENCHMARKS.md](16-PERFORMANCE-BENCHMARKS.md) once formally benchmarked — no target number is asserted here until measured; Phase 11 observed, informally, a full generate-then-score run completing well under a second for the 15-lab dev dataset).
- **NFR-04 (Scalability)** The academic hierarchy, lab count, and batch count must be data-driven; no code change should be required to add a program, stream, division, batch, or lab.
- **NFR-05 (Maintainability)** ✅ Each hard constraint is an independently implemented, independently testable unit (`SchedulingConstraint` implementation) rather than embedded in a monolithic conditional. *(Phase 9 — twelve `@Component` classes, one test class each.)*
- **NFR-06 (Reliability)** A cancelled or rejected allocation is never physically deleted; history is preserved via status transitions.
- **NFR-07 (Auditability)** Every consequential mutation produces an audit record sufficient to answer "who did what, when, to which resource."
- **NFR-08 (Testability)** ✅ Scheduling domain objects (candidate, context, constraint result, score breakdown, recommendation/explanation) are decoupled from JPA entities and HTTP controllers so they can be unit tested without a database or web layer. *(Phase 8/9/11/12 — verified: none of `SchedulingRequest`/`SchedulingContext`/`CandidateAllocation`/`ConstraintResult`/`ConstraintViolation`/`ConstraintEvaluation`/`ScoreContribution`/`ScoredCandidate`/`AllocationRecommendation`/`ExplainedValidCandidate`/`RejectedCandidateExplanation` carries a JPA annotation; the large majority of this project's unit tests construct these directly with no Spring context.)*
- **NFR-09 (Usability)** ✅ Every recommended or rejected allocation candidate is explainable in structured, non-recomputed detail, not just a status code. *(`ExplainableAllocationService`, Phase 12 — implemented and verified: a recommended candidate carries its exact Phase 11 score breakdown plus a display-labeled constraint-check summary; a rejected candidate carries every `ConstraintViolation` it failed, converted to a display-labeled `ViolationExplanation`, never collapsed to the first reason. "Plain language" here means structured explanation objects with both a machine code and a human display label — not free-form NLG/LLM text, deliberately, for determinism (docs/05-SCHEDULING-ENGINE.md). Not yet reachable through any end-user UI — Phase 15/18.)*
- **NFR-10 (Data Integrity)** ✅ Time-overlap logic uses proper half-open interval comparison (`startA < endB AND startB < endA`), never naive equality checks. *(`TimeIntervalUtils`, Phase 7, extended Phase 9 with an `Instant` overload for HC-06 — reused by every conflict-related constraint, never reimplemented per-constraint.)*
