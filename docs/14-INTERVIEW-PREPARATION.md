## Elevator Pitch (30 seconds)

"I built a constraint-based lab scheduling system for a college's multi-program academic structure. Instead of a simple booking form, it runs every request — official timetable or student-rep-submitted extra practical — through a constraint engine that checks lab conflicts, faculty conflicts, faculty availability, capacity, and software requirements, then ranks the valid options with a scoring model, and can even auto-generate a full multi-session timetable using backtracking search. It also handles the tricky real case where two different batches in the same division can share a time slot as long as their lab and faculty don't collide."

## 2-Minute Explanation

**Problem:** A college has ~15 shared labs, several programs/streams/divisions/batches, and needs to allocate lab practicals so that no lab, faculty member, or student batch is double-booked — while allowing legitimate simultaneous use (different batches, different labs, different faculty). On top of the official semester timetable, class representatives book ad-hoc makeup labs that must obey the exact same rules, checked live against everything else already booked.

**Architecture:** React/TypeScript frontend, Spring Boot backend, PostgreSQL, as a modular monolith — not microservices, because there's no independent-scaling need at this size, and keeping the FCFS booking transaction inside one process/database makes correctness far easier to guarantee than a distributed alternative would.

**Scheduling engine:** A pipeline of independently-testable hard constraints (lab conflict, faculty conflict, faculty availability, batch conflict, division-wide conflict, capacity, software/equipment/lab-type requirements, authorization, academic-relationship validity) filters candidate labs; a weighted scoring model then ranks the *valid* survivors on capacity fit, environment fit, utilization balance, and schedule-gap minimization. For full-timetable generation, a most-constrained-first backtracking search assigns the hardest-to-place sessions first and backtracks when a later session runs out of options.

**Database:** PostgreSQL with an explicit `target_type` (BATCH/DIVISION) on the allocation table — this is the key modeling decision that correctly distinguishes "this batch is busy" from "the whole division is busy," which a naive boolean flag would get wrong.

**Security:** JWT auth, three roles (Lab Assistant, CR, Student), and — critically — every ownership check (which division a CR may act on) is resolved server-side from the authenticated user's assignment record, never trusted from a client-supplied ID.

**Testing:** JUnit/Mockito unit tests per constraint, Testcontainers-backed integration tests for the full request pipeline, and a dedicated concurrency test proving that two simultaneous conflicting booking requests can never both succeed.

**Results:** `TO BE VERIFIED AFTER IMPLEMENTATION` — performance numbers and test-pass status will be added here once Phases 9–25 actually produce them.

## Likely Interview Questions — Design-Level Answers

**Why is this not CRUD?** A CRUD app checks "is this row taken?" This system generates and ranks multiple valid candidates, distinguishes batch-level from division-wide occupancy, runs a backtracking search for multi-session generation, and guarantees correctness under concurrent writes — none of which a form-over-database app does.

**Why Java / Spring Boot?** Strong static typing suits a domain this relationally strict (labs, faculty, batches, terms all cross-reference each other); Spring's transaction management is what makes the FCFS/concurrency guarantee tractable; the JUnit/Mockito/Testcontainers ecosystem lets the scheduling engine be tested in real isolation from the web and persistence layers.

**Why PostgreSQL?** The data is inherently relational (foreign keys everywhere), and the concurrency-safety requirement depends directly on transactional/locking guarantees a relational database provides natively.

**Why not MongoDB?** A document store would push conflict-prevention entirely into application code, re-creating the exact check-then-insert race condition this project is specifically designed to eliminate; it also offers no benefit for data this uniformly relational, and loses foreign-key integrity for no upside.

**Why not Node as another backend hop (React → Node → Java)?** It would add a second runtime, a duplicated API/domain layer, and another failure boundary, without adding any capability — Spring Boot already serves the API directly to React over REST/JSON.

**Why modular monolith?** No requirement here calls for independent deployment or scaling of sub-parts; a single deployable with clear internal package boundaries (`constraint`, `scoring`, `conflict`, `scheduler`) gets the same separation of concerns with far less operational overhead, and keeps the FCFS-safety transaction inside one process.

**What is a hard constraint?** A rule that, if violated, makes a candidate invalid regardless of how well it scores — e.g. lab conflict, faculty conflict, capacity. See [06-CONSTRAINTS.md](06-CONSTRAINTS.md).

**What is a soft constraint?** A ranking factor among already-valid candidates — e.g. capacity fit, utilization balance. See [07-ALLOCATION-SCORING.md](07-ALLOCATION-SCORING.md). Critically, no hard constraint is ever expressed as a soft penalty in this system — the scoring engine only ever ranks candidates that already passed every hard check.

**Why backtracking?** Because a greedy, single-pass assignment can leave a later session with zero valid options even though a different (still valid) earlier choice would have left room for everyone — backtracking retries earlier decisions rather than declaring outright failure.

**Why most-constrained-first?** Scheduling the session with the fewest valid candidates first, while the most resource slack still exists, minimizes the chance of a costly late-stage backtrack; flexible sessions are safest to schedule last because they have the most alternatives.

**What is the complexity?** Worst-case exponential — this is a CSP, not claimed to be polynomial. Practical performance depends on hard-constraint pre-filtering keeping branching factors small, plus a configured `maxAttempts`/`maxDepth`/`timeout` budget that bounds runtime at the cost of possibly returning a partial rather than full schedule. Real numbers: `TO BE VERIFIED AFTER IMPLEMENTATION`.

**How can different batches run simultaneously?** Because occupancy is tracked at the batch level (`target_type = BATCH`) unless a session is explicitly division-wide (`target_type = DIVISION`) — two different batches booking at the same time is only flagged as a conflict if they also collide on lab or faculty, which are checked completely independently.

**How do you prevent faculty clashes?** A dedicated hard constraint (HC-02) checks every active allocation for the same faculty on the same date using half-open interval overlap — regardless of batch, division, or lab, one faculty member can never have two overlapping sessions.

**How do you prevent lab clashes?** Same mechanism (HC-01), scoped to `lab_id` instead of `faculty_id`.

**How will FCFS remain safe under concurrent requests?** By making the constraint check and the insert happen inside a single database transaction with an appropriate isolation/locking strategy (finalized in Phase 16; see [15-DESIGN-DECISIONS.md](15-DESIGN-DECISIONS.md) ADR-010), rather than a check-then-insert pattern with a race window between the two steps. Verified with a real concurrent-request integration test before being called done.

**Why manually approve PDF extraction?** Table/OCR extraction from PDFs is not reliably accurate; publishing directly from extraction risks silently corrupting the official timetable with mis-read subjects, labs, or times. A human review-and-correct step is cheap insurance against that.

**How will you scale this later?** `TO BE VERIFIED AFTER IMPLEMENTATION` — see [18-FUTURE-IMPROVEMENTS.md](18-FUTURE-IMPROVEMENTS.md) for the honest list of what would need to change (e.g., a real solver like OR-Tools if problem size grows by orders of magnitude, splitting the scheduling engine into its own service only if it needed independent scaling).

## Trade-Off Answers

**What would you change with more time?** Likely a dynamic re-ordering variant of most-constrained-first during backtracking (currently computed once per run), and a proper OR-Tools comparison benchmark to quantify what a general solver buys over the custom engine.

**When would a mathematical solver become useful?** If the problem grows to genuinely large scale (many campuses, hundreds of divisions, full-semester joint optimization across every subject at once) where provable optimality — not just a valid, reasonably good schedule — becomes worth the added integration complexity.

**What happens with 1000 labs?** The current design's indexing strategy (partial indexes on `(lab_id, date)` etc., see [04-DATABASE-DESIGN.md](04-DATABASE-DESIGN.md)) should hold up; the more interesting pressure point would be candidate-generation breadth in the backtracking search, which is where a real solver's constraint propagation would start to matter more than at the current ~15-lab scale.

## Authentication & RBAC (Phase 3 — implemented, verified answers)

**How does authentication work?** The frontend posts email/password to `POST /api/auth/login`. The backend looks up the user by normalized (trimmed, lowercased) email, verifies the password with BCrypt, checks the account is active, and — if all three pass — signs a JWT (HS256) containing only the user id and role, returned alongside a safe user summary. Every subsequent request carries that JWT in an `Authorization: Bearer` header; a servlet filter validates it and re-fetches the user from the database on every single request (not just at login) before populating Spring Security's context.

**Why JWT?** It keeps the API stateless — no server-side session store to synchronize or scale — which fits a REST API cleanly. The trade-off (a token can't be instantly revoked before it expires) is accepted for this project's scope and mitigated by keeping the expiration short (60 minutes) and by re-checking the user's `active` flag on every request, so *deactivation* still takes effect immediately even though the token itself remains technically valid until expiry.

**How does Spring Security validate requests?** A custom `OncePerRequestFilter` (`JwtAuthenticationFilter`) runs before Spring Security's standard authentication filter. It extracts the bearer token, verifies its signature and expiration via the `io.jsonwebtoken` library, looks the user up fresh in the database, and — only if the user still exists and is active — populates the `SecurityContext` with an authority of `ROLE_<role>`. If any step fails, no authentication is set, and Spring Security's own access-control rules (`anyRequest().authenticated()`) reject the request with a `401` produced by a custom `AuthenticationEntryPoint` that writes the project's standard JSON error shape instead of Spring's default HTML page.

**How are passwords stored?** BCrypt hashes, via `BCryptPasswordEncoder` — never plaintext, never logged, never returned by any endpoint (verified: the safe `UserSummary` DTO returned by both `/login` and `/me` has no password field at all, so there is nothing to accidentally serialize).

**Why hashing instead of encryption?** Encryption is reversible by design (given the right key) — exactly the property you don't want for credential storage, since it means a compromised key (or a rogue insider) could recover every password. Hashing is one-way; BCrypt specifically also embeds a random salt per password, so identical passwords never produce identical stored hashes, defeating precomputed rainbow-table attacks.

**How does RBAC work?** Roles are an enum (`LAB_ASSISTANT`, `CR`, `STUDENT`) persisted as a string, never an ordinal. Spring Security's method security (`@EnableMethodSecurity`, `@PreAuthorize("hasRole(...)")`) is wired up and proven against a test fixture (no real role-restricted business endpoint exists yet — that arrives with the academic/lab domain in Phase 4+, at which point `@PreAuthorize` gets applied to real controller methods).

**Why are frontend role checks insufficient?** A `RequireRole` component hides UI for the wrong role, but it's just JavaScript running in the user's own browser — anyone can open devtools and force it to render, or call the API directly with curl/Postman. The actual authorization decision is made server-side, on every request, by Spring Security; the frontend check exists purely so the UI doesn't show controls a user isn't allowed to use, not to prevent misuse.

**What is 401 vs 403?** `401 Unauthorized` means "I don't know who you are" — no token, an invalid/expired token, or a token for a deactivated/deleted user. `403 Forbidden` means "I know who you are, and you're not allowed to do this" — an authenticated request that fails a role/ownership check. The project uses distinct handlers (`RestAuthenticationEntryPoint` for 401, `RestAccessDeniedHandler` for 403) so both cases produce the same JSON error shape as every other endpoint, never Spring's default HTML error page.

**Why stateless authentication?** No `HttpSession` is created or read (`SessionCreationPolicy.STATELESS`); the JWT itself is the complete artifact of "being logged in." This also directly informed the CSRF decision: CSRF protection defends against a browser automatically replaying an ambient credential (a cookie), and there is no such credential here — the token is only ever sent because the frontend's own JavaScript explicitly attaches it, so CSRF protection was disabled with that specific reasoning documented, not out of convenience.

**What are JWT trade-offs?** No instant server-side revocation short of waiting out the expiration (mitigated here by re-checking the `active` flag on every request, so deactivation is still immediate even if the token itself isn't "revoked" in the cryptographic sense); the token's claims are a snapshot from login time, which is exactly why claims are kept minimal (id + role only) and why anything that can change mid-session (like CR division ownership, once that exists) is resolved fresh from the database, never trusted from the token.

**Where is the token stored and why?** `localStorage` in the browser — a deliberate, documented choice (not the default), trading a real XSS-read risk for simplicity (no CSRF-token plumbing, trivial to attach to every request) appropriate for this project's current scope. See ADR-015 in [15-DESIGN-DECISIONS.md](15-DESIGN-DECISIONS.md) for the full trade-off analysis, including the HttpOnly-cookie hardening path.

**How can this be hardened for production?** Move the token to an HttpOnly, `Secure`, `SameSite=Strict` cookie (removes the XSS-read risk, but requires re-enabling CSRF protection scoped to state-changing requests); consider shorter-lived access tokens paired with a properly-secured refresh-token flow if session length becomes a real UX problem; generate the JWT signing secret via a real secrets manager rather than an environment variable in `.env`. None of this is implemented yet — it's the honest next-step list, not a claim of what exists today.

## Academic Domain & RBAC-Ownership (Phase 4 — implemented, verified answers)

**Why no `Student` table?** Capacity checks (the only thing that would need per-student data) only ever need a single headcount number per batch/division, not individual records — `strength` is a plain, required, positive integer column on both `Batch` and `Division`. Building and maintaining a `Student` table (enrollment, transfers, dropouts) for a number that's used exactly one way would be real ongoing effort for zero scheduling benefit.

**Why store batch/division strength directly instead of deriving it?** Same reason as above — there's no second use of "how many students" anywhere in the system's actual requirements yet. If per-student features (attendance, individual timetables) become a real requirement, `Student` is an additive migration at that point, not a rework.

**How is the academic hierarchy modeled?** `Program → Stream → AcademicYear → Division → Batch`, each a real table with a foreign key to its parent — not a single denormalized "class" table. `AcademicTerm` (a semester/time period, e.g. "Semester 5, 2026-27") is deliberately a *separate*, independent concept from `AcademicYear` (the program's *study year*, e.g. "Year 3") — conflating the two was a real risk the naming was chosen specifically to avoid.

**Why are Program and Stream database entities instead of enums?** Because the college's actual structure (which programs, which streams under each) is data an administrator should be able to change without a code deployment — hardcoding "CS," "IT," "AIML" etc. as Java enum constants would mean every new program or stream requires a rebuild. Enums are reserved for genuinely stable application concepts (`UserRole`, `TermStatus`) that the *application's own logic* branches on, not for college-specific configuration.

**How do you model a variable number of batches?** `Batch` has a foreign key to `Division` and nothing caps how many batch rows can point at the same division — the schema has no notion of "exactly two batches" anywhere, and the seed data deliberately uses three (A1/A2/A3) specifically to prove the model isn't hardcoded to two.

**How do you prevent a batch from being attached to the wrong division?** A batch's `division_id` foreign key guarantees it belongs to *some* real division, but not necessarily the *specific* division a request claims — that cross-table relationship can't be a database `CHECK` constraint in PostgreSQL (a `CHECK` can't query another table). It's validated explicitly in `SubjectFacultyAssignmentService.create()`, which compares `batch.getDivision().getId()` against the division actually specified in the request and throws `INVALID_ACADEMIC_RELATIONSHIP` (400) if they don't match. Proven both by a unit test with mocked entities and by an end-to-end test hitting the real endpoint with two real divisions.

**Why is Faculty separate from User?** Faculty never log in — they're referenced by scheduling data (and later, availability), but there's no account, password, or JWT identity for them. Modeling them as an `app_user` row would mean building auth infrastructure (password reset, login) for people who structurally never need it, and would blur the "exactly three login roles" boundary the whole authorization model is built around.

**How does subject-faculty assignment work?** `SubjectFacultyAssignment` connects a subject, a faculty member, a division, an academic term, and an *optional* batch. A null batch means "this faculty covers the whole division for this subject/term" — not "unknown batch." Two partial unique database indexes (one for batch-scoped rows, one for division-scoped rows) guarantee at most one active assignment per scope, so the data can never be ambiguous about who teaches what.

**How does batch-level faculty override division-level assignment?** `FacultyAssignmentResolutionService` checks for an exact batch-level match first; only if none exists does it fall back to the division-level assignment. Because the database guarantees at most one active row per scope (see above), this resolution never has to choose between two "equally valid" options — only between "more specific" and "more general," which always has one correct answer.

**What is the difference between RBAC and resource ownership?** RBAC answers "is this user even the right *kind* of user" (role authorization — `@PreAuthorize("hasRole('LAB_ASSISTANT')")`, checked before any business logic runs, with no idea *which* resource is involved). Ownership answers "is this user allowed to touch *this specific* resource" (`CrOwnershipService.requireOwnsDivision`, a runtime database lookup that no static role annotation could express). Both are needed — role authorization alone would let any CR act on any division as long as they're a CR at all.

**How do you stop a CR from scheduling another division later?** The mechanism (`CrOwnershipService`) is built and tested now, even though no scheduling endpoint exists yet to use it: it resolves the caller's division purely from their authenticated `userId` via their own `CrAssignment` row, and a client-supplied `divisionId` is only ever compared against that resolved value, never trusted as authorization on its own. Proven directly with a test where a CR assigned to Division A is denied when asked to act on Division B.

**Why preserve historical CR assignments?** Reassigning a CR (e.g. a new class representative each semester) ends the old assignment (`status → ENDED`, `validTo` set) rather than deleting or overwriting the row — so "who was the CR for Division A last semester" remains answerable, and any audit trail referencing that assignment stays valid. This mirrors the same historical-preservation principle used for `Allocation` cancellation (Phase 1 design) and CR account deactivation (Phase 3).

**What was the most difficult / interesting bug so far?** Two, both found during this phase's Docker-based manual verification, not by unit tests alone: (1) `@PreAuthorize` role denials were returning `500` instead of `403`, because the denial exception is thrown deep inside Spring MVC's own dispatch (the controller-method AOP proxy) and was being caught by the project's own global `@RestControllerAdvice` before it could ever reach Spring Security's dedicated access-denied handling — fixed by adding an explicit handler for it. (2) Several read endpoints threw `LazyInitializationException` because their DTO-mapping code touched lazy JPA associations *after* the transaction (and Hibernate session) had already closed — fixed by adding `@Transactional(readOnly = true)` to the relevant service methods, and in one case moving DTO mapping fully inside a transactional method. Both are documented in detail below and in ASSUMPTIONS.md (A-23, A-24) — real bugs, root-caused, fixed, and re-verified, not glossed over.

## Laboratory Domain (Phase 5 — implemented, verified answers)

**How do you model labs?** `Lab` has a stable, unique, user-facing `code` (e.g. "C-304") that's immutable after creation — allocation explanations will reference this code, never the database id. Capacity, a lab type reference, and a flat wing/floor/room location are the other core fields. `active=false` means permanently retired, distinct from `LabUnavailability` (a temporary, dated closure).

**Why is `LabType` data instead of an enum?** Same reasoning as `Program`/`Stream` in Phase 4: the set of lab types is something a Lab Assistant should be able to extend (a future "Electronics Lab," say) without a code deployment. Enums in this codebase are reserved for genuinely stable application concepts the code itself branches on (`UserRole`, `TermStatus`), not for college-specific configuration.

**How do you represent software installed in many labs?** A many-to-many relationship between `Lab` and `Software`, materialized as an explicit `LabSoftware` association entity (not an implicit `@ManyToMany`) so it can carry per-installation metadata (`installedVersion`) that a plain join table can't hold without a later migration to convert it into a real entity anyway.

**Why use explicit association entities instead of simple `@ManyToMany`?** Because the association isn't just "does this pair exist" — `lab_equipment.quantity` ("10 routers" vs "1 router") and `lab_software.installedVersion` are real facts the phase's own requirements called out as useful. Building the explicit entity now costs almost nothing extra and avoids a schema migration later when that metadata inevitably gets used.

**How do you distinguish permanent lab deactivation from temporary maintenance?** Two different mechanisms, not one flag doing double duty: `Lab.active` for permanent retirement, `LabUnavailability` (dated, half-open interval rows) for temporary administrative closures. They have different query semantics — a permanently inactive lab should never be a candidate anywhere; a temporarily unavailable lab is a normal candidate outside its specific closed window.

**Why does the database store capacity?** Because it's a hard, structural property of the physical room — the number of workstations or seats doesn't change per-request, and every future capacity check (HC-07) needs a stable, queryable source of truth rather than recomputing or guessing it. `capacity > 0` is enforced both by a Bean Validation annotation and a database `CHECK` constraint.

**Why not compute availability entirely in the frontend?** Two separate reasons: first, the general project principle that the frontend is never the source of truth for anything security- or correctness-relevant (the backend would still need to validate on write, so computing in the frontend would just be redundant, unverified work). Second, more specifically for Phase 5: the static capability filters (`GET /api/labs?minCapacity=...&software=...`) already require a real database query (an `EXISTS` subquery per required software/equipment code) — loading all 15+ labs into the browser and filtering client-side would not scale as the lab count grows and would duplicate query logic in two languages for no benefit.

**Why are software/equipment capabilities separate from subject requirements?** Phase 5 stores what a lab *has*; a subject's requirements (what it *needs*) don't exist until Phase 6. Mixing them now would mean guessing at the requirements model before it's actually designed — the phase brief was explicit that Phase 5 must not add `SubjectSoftwareRequirement`/`SubjectEquipmentRequirement` yet.

**How would Cloudera filtering work?** `GET /api/labs?software=CLOUDERA` (or combined with `minCapacity=68`) runs a `Specification<Lab>` that adds an `EXISTS` subquery against `lab_software` for each requested software code, ANDed together for **ALL**-match semantics (a lab must have every requested software, matching how HC-08 will eventually require *all* of a subject's listed software, not just one). Verified directly: of 15 seeded labs, exactly 3 have Cloudera, and only those 3 are returned by the filter; combining it with `minCapacity=68` correctly narrows to just the 2 that satisfy both.

**Why keep `open-in-view` disabled?** Because it trades a loud, obvious failure at development time (a `LazyInitializationException` on an under-tested code path) for a silent, easy-to-miss N+1 query problem at runtime in production. Phase 4 hit this directly — see the next answer.

**How did Phase 4 expose `LazyInitializationException` and what did you learn?** See the "Real Engineering Problems Encountered" section below for the full account. The short version: several read endpoints mapped entities to DTOs *after* their transaction had already closed, so touching a lazy association threw. The fix was consistently applying `@Transactional(readOnly = true)` at the service layer for any read path whose DTO mapping touches a lazy field. The lesson carried directly into Phase 5: every new lab-domain service follows the same class-level `@Transactional(readOnly = true)` pattern from the start, and `LabService.toFullResponse()` deliberately composes the software/equipment lists *inside* the service, not in the controller after the fact — applying the Phase 4 lesson proactively instead of waiting to hit the same bug again.

## Subject Requirements (Phase 6 — implemented, verified answers)

**How do subject requirements differ from lab capabilities?** Phase 5 stores what a lab *has* (`LabSoftware`, `LabEquipment`). Phase 6 stores what a subject *needs* (`SubjectSoftwareRequirement`, `SubjectEquipmentRequirement`, lab-type requirement). The two sides are deliberately never joined or compared in Phase 6 — that comparison is the Constraint Engine's job (Phase 9). Verified manually by querying each side independently (`GET /api/subjects/{id}/requirements` and `GET /api/labs?software=CLOUDERA`) and confirming neither endpoint references the other.

**Why are requirements optional?** Not every subject has a technical prerequisite — a theory-only subject has zero rows in either requirement table and a `null` lab-type requirement, and that's a valid, expected state, not an error condition. CNS was seeded specifically with zero requirements to prove this path works, distinct from BDA which has real requirements.

**How do you model "must have ALL of these software packages," not just "any one of them"?** Each row in `subject_software_requirement` is one required software item; a subject with two rows needs both. There's no OR/ANY semantics anywhere in this table — the same ALL-required philosophy as Phase 5's lab-side capability filter (`LabSpecifications.hasAllSoftware`), so the two sides will compare cleanly once the constraint engine reads both.

**Why no boolean `required` column instead of every row being implicitly required?** Because nothing in this project yet needs a soft/preferred capability concept, and adding an unused flag would be exactly the kind of speculative column the project avoids. See ADR-026 (docs/15-DESIGN-DECISIONS.md).

**How do you model required vs. preferred lab type as genuinely distinct?** Two separate nullable FK columns on `subject` — `required_lab_type_id`, `preferred_lab_type_id` — enforced to never both be set, at both the application layer (`Subject.setLabTypeRequirement()` throws `INVALID_LAB_TYPE_PREFERENCE`) and the database layer (a `CHECK` constraint). A single column with a "hard/soft" flag was rejected because a nullable-FK pair makes the invalid "both set" state structurally impossible rather than just application-policed. See ADR-027/ADR-028.

**Why does equipment carry a `requiredQuantity` but software doesn't?** Equipment is physically countable — a subject might need 30 oscilloscopes for a batch of 60 working in pairs — while software is a presence check (a license is installed or it isn't); a quantity on software would be meaningless in this system's model. See ADR-029.

**What happens if you try to add a requirement referencing inactive software/equipment/lab type?** Rejected with `INACTIVE_SOFTWARE`/`INACTIVE_EQUIPMENT`/`INACTIVE_LAB_TYPE` — a subject shouldn't be able to require something the Lab Assistant has already retired from the catalog, which would create an unsatisfiable requirement no lab could ever meet.

**What happens on a duplicate requirement?** `DataIntegrityViolationException` from the unique constraint (`subject_id, software_id` / `subject_id, equipment_id`) is caught and translated to `SOFTWARE_REQUIREMENT_ALREADY_EXISTS`/`EQUIPMENT_REQUIREMENT_ALREADY_EXISTS` — a domain-specific 409, never a raw SQL error, following the same `AMBIGUOUS_FACULTY_ASSIGNMENT`/`DUPLICATE_ASSIGNMENT` precedent from Phase 4.

**Who can mutate requirements?** Only `LAB_ASSISTANT`, enforced via `@PreAuthorize` on every write endpoint. CR and STUDENT can read (`GET /api/subjects/{id}/requirements`) but never write — verified against the running stack with the full RBAC matrix (LAB_ASSISTANT succeeds, CR/STUDENT get 403, unauthenticated gets 401).

**Why is requirement scope on `Subject` and not something per-term?** A subject's technical prerequisites are a curriculum fact, not a scheduling fact — BDA needing Cloudera doesn't change term-to-term. This mirrors ADR-018's earlier rejection of a `SubjectOffering` entity for the same reason. See ADR-025.

**How would you extend this to version-pinned requirements (e.g. "Cloudera >= 6.3") later?** Not modeled in Phase 6 — requirements match by software/equipment identity only, even though `LabSoftware.installedVersion` is already stored from Phase 5. Adding version comparison would need a new column and comparison operator on the requirement row; deliberately deferred rather than guessed at now, since no real scenario in this project needs it yet. See ADR-030.

**Are there any new bugs from this phase?** No — the implementation compiled and passed all unit tests (33/33) on the first attempt, and manual Docker verification found no defects. This is a genuine "clean phase," attributed to proactively applying lessons learned in Phase 4/5 (class-level `@Transactional(readOnly = true)` from the start, self-contained DTO records, public `getEntity()` accessors) rather than discovering them again the hard way.

## Faculty Availability (Phase 7 — implemented, verified answers)

**How is faculty availability represented?** A recurring weekly window — `faculty_id`, `academic_term_id`, `day_of_week` (`java.time.DayOfWeek`), `start_time`/`end_time` (`LocalTime`), `active`. It is a *declared boundary* ("I can teach Monday mornings this semester"), never an actual booked session — that distinction (availability vs. conflict) is the single most important concept in this phase.

**Why is it term-scoped, and why mandatorily rather than optionally?** Because real availability changes semester to semester (the classic example: Monday mornings free in one term, Monday afternoons in the next), and every other term-relative fact in this project (`SubjectFacultyAssignment`, `CrAssignment`) is already mandatorily term-scoped — an optional/nullable "applies forever" design (the original Phase 1 draft, since superseded) would have been the one inconsistent case, and risks silently going stale the moment a faculty's real schedule changed. See ADR-031.

**Why `java.time.DayOfWeek` + `LocalTime` instead of strings or integers?** `DayOfWeek` is a stable, well-known JDK enum — no risk of "1 = Monday vs 1 = Sunday" ambiguity that a raw integer ordinal would invite, and it's persisted as its name string (`MONDAY`, not an ordinal) so the stored value is directly human-readable in the database, not just in application code. `LocalTime` is the correct JDK type for "a time of day with no date/timezone attached" — exactly what a recurring weekly slot needs; storing `"09:00"` as a string would require re-parsing and re-validating on every read, and would silently accept malformed input a real type cannot.

**Why not store time as strings like `"9-11"` or `"09:00 AM"`?** Because a string has no enforced structure — nothing stops `"9-11"`, `"9 to 11am"`, or a typo from being persisted, and every consumer would need to re-parse and re-validate it defensively. `LocalTime` columns (backed by PostgreSQL `TIME`) make malformed input structurally impossible past the JDBC boundary, and comparison/arithmetic (`isBefore`, `isAfter`) is native and correct, not string-comparison-that-happens-to-work.

**What are half-open intervals, and why use them here?** `[startTime, endTime)` — the start instant belongs to the interval, the end instant does not. This is the same convention used everywhere else time ranges appear in this project (`LabUnavailability`, and every hard constraint in docs/06-CONSTRAINTS.md). Its practical payoff: back-to-back windows like `09:00-11:00` and `11:00-13:00` correctly do **not** overlap — the boundary instant belongs only to the second interval — which is exactly the "adjacent, not overlapping" behavior this phase needed for merge-free multi-window availability.

**How do you detect overlap?** The standard half-open formula: `startA < endB AND startB < endA`. Implemented once in `TimeIntervalUtils.overlaps(...)` (`com.college.laballocation.common`) specifically so this project's future constraint classes (`FacultyConflictConstraint`, `LabConflictConstraint`, `FacultyAvailabilityConstraint` — all Phase 9+) can reuse the exact same formula rather than each reimplementing it slightly differently.

**What does a faculty with zero availability rows for a given term/day mean?** Unavailable — never "available all day." This is a deliberate application-layer semantic (`FacultyAvailabilityService.isAvailable` returns `false` on an empty result), explicitly called out because the opposite interpretation (missing data = no restriction) is the more dangerous default for a hard-constraint input: it would silently make every unconfigured faculty schedulable everywhere, exactly backwards from the safe failure mode.

**Can a faculty have multiple availability windows per day?** Yes — e.g. `09:00-11:00` and `14:00-16:00` on the same Monday, with a genuine unavailable gap between them. No uniqueness constraint limits a faculty to one row per day; only *overlapping* active rows for the same faculty/term/day are rejected.

**How do you handle adjacent intervals — stored as two rows or merged into one?** Stored as two separate rows, deliberately never merged at write time (keeps administrative intent explicit — did the Lab Assistant mean to enter two windows, or extend one? Merging would obscure that). But during *evaluation only*, `FacultyAvailabilityService.isAvailable` folds directly-adjacent active rows together in memory (never touching the database) so a requested session spanning the adjacency boundary — e.g. `10:00-12:00` against stored `09:00-11:00` + `11:00-13:00` — is still correctly found available. See ADR-032.

**What is the difference between Faculty Availability and Faculty Conflict?** Two independent layers that must both pass. Availability (HC-03, this phase) is a static, declared weekly boundary — "can this faculty ever teach Monday 10-11am, per their general schedule?" Conflict (HC-02, Phase 9+) depends on real allocation data — "is this faculty already booked for something else at this exact date/time?" A faculty can be generally available at a time they are already booked; the two checks answer genuinely different questions and neither substitutes for the other.

**Why is availability a hard constraint rather than a scoring factor?** Because scheduling a faculty member outside their declared availability isn't a *worse* choice among valid ones — it's not a real choice at all; the person may not physically be present/able to teach then. Hard constraints represent physical/administrative impossibility; soft constraints (scoring) represent preference among genuinely valid options. This mirrors the same reasoning documented in docs/07-ALLOCATION-SCORING.md for why HC-08/HC-09/HC-10 are never re-scored as soft factors.

**How will the future scheduling engine consume this?** Not through the REST API — `FacultyAvailabilityConstraint` (Phase 9+, a `SchedulingConstraint` per docs/05-SCHEDULING-ENGINE.md) will call `FacultyAvailabilityService.isAvailable(...)` directly as an internal Spring bean dependency, the same way any other service-to-service call works in this codebase. This is also why `/api/faculty/{id}/availability*` was restricted to `LAB_ASSISTANT`-only (ADR-034) — the constraint engine never needs REST access to its own process's data.

**Why is read access restricted to LAB_ASSISTANT here, unlike Labs/Subject Requirements where any authenticated role can read?** Because unlike lab capacity or subject requirements (genuinely useful context for a CR planning a request), raw faculty-availability rows have no demonstrated CR/STUDENT use case yet — this project's default is to open read access only where a real need exists, not because other domains happened to open theirs. See ADR-034; this can be loosened later without a breaking change if a real need appears.

## Scheduling Domain & Allocation Persistence (Phase 8 — implemented, verified answers)

**What is the difference between `Allocation` and `CandidateAllocation`?** `Allocation` is a persisted JPA entity representing a session that actually happened (or was formally decided) — created only once already known valid. `CandidateAllocation` is a plain, unpersisted record representing one possibility (a specific candidate lab) still being evaluated. Most candidates are rejected and discarded; only a winning one ever becomes a real `Allocation`.

**Why is `CandidateAllocation` not persisted?** Persisting every candidate considered during a scheduling run — most of which fail hard constraints and are thrown away — would be pure waste, and would blur "this was actually booked" with "this was considered and rejected," a distinction NFR-08 and this project's whole constraint-based premise depend on staying clear. See ADR-038.

**Why do you use `ScheduleVersion`?** So an official timetable revision never silently overwrites history — publishing a new version supersedes (never deletes) the term's previous published version, which is what lets students always see exactly one current version while every prior revision remains queryable (ADR-009).

**Why preserve historical schedule versions instead of editing in place?** Because "what was the timetable actually like on the day a student attended" is a real, answerable question this project's audit/history requirements care about (NFR-06/NFR-07) — in-place edits would destroy that history the moment a correction was made.

**Why does `Allocation` contain both `divisionId` and an optional `batchId`?** Every allocation belongs to a division regardless of its target type (`division_id` is always set); `batch_id` is only set for `BATCH`-targeted sessions. This single design choice is what makes HC-05's bidirectional division/batch conflict check answerable with one query (`findActiveForDivision`) instead of two separately-joined ones — see ADR-005 and docs/06-CONSTRAINTS.md HC-05.

**How do you model BATCH vs. DIVISION?** An explicit `target_type` enum column (`BATCH`/`DIVISION`), not an implicit null-as-signal — enforced twice: `Allocation.forBatch`/`.forDivision` are the only constructors, and a database CHECK constraint (`chk_allocation_target_invariant`) backstops the same rule even against a hypothetical future application bug. The cross-table "does this batch actually belong to this division" half can't be a CHECK constraint (Postgres can't query another table in one), so `forBatch` checks it directly against the already-loaded `Batch` entity's `Division`.

**Why store allocation date/time as `LocalDate`/`LocalTime` instead of `TIMESTAMPTZ`?** A session is inherently a single local-college-day event with no cross-timezone ambiguity relevant to *scheduling* it — matching `faculty_availability`'s shape (Phase 7) means `TimeIntervalUtils` is directly reusable with zero conversion for the four allocation-vs-allocation conflict checks (HC-01/02/04/05), which are the overwhelming majority of what needs this data. See ADR-036.

**How do you bridge `LocalDate`/`LocalTime` with `LabUnavailability`'s `TIMESTAMPTZ`?** `SchedulingTimeMapper` — a single, central, tested component (`toInstant`/`toInstantRange`) that combines a date, a local time, and a configurable college `ZoneId` into a real `Instant`. Introduced now, ahead of Phase 9 actually needing it for HC-06, specifically so this conversion is solved once rather than reinvented ad hoc inside `LabAvailabilityConstraint` or duplicated by some future second consumer.

**Why use a configurable `ZoneId` instead of a hardcoded offset like "UTC+5:30"?** A manual offset is silently wrong the moment any DST rule ever applies to the deployment zone, and it hides an important decision as an unlabeled magic number. `ZoneId`/`Instant` delegate to the JDK's own correct, maintained zone-rule database — the college's actual zone is one line of configuration (`COLLEGE_TIME_ZONE`), never scattered arithmetic.

**Why don't you expose an allocation-create API yet?** Because an `Allocation` is only ever supposed to exist once it's already known valid, and nothing in this codebase can determine that yet — the constraint engine (Phase 9) doesn't exist. Opening a creation endpoint now would mean accepting arbitrary, unvalidated bookings, directly contradicting the entire premise of a constraint-based system. Verified live: `POST /api/allocations` returns `404`. See ADR-039.

**Why are constraints a separate Phase 9 layer instead of built alongside the schema now?** Because "what a candidate/allocation *is*" (Phase 8 — the schema, the object shapes, the query infrastructure) and "whether a candidate is *valid*" (Phase 9 — the actual constraint logic) are genuinely different concerns with different dependencies; Phase 9 needs Phase 8's persisted data to exist first, so building them together would just mean building Phase 8 first anyway, without the clean phase boundary that keeps each one's own tests focused and reviewable.

## Constraint Engine (Phase 9 — implemented, verified answers)

**What is the Constraint Engine?** A component (`ConstraintEngine`) that takes one `SchedulingContext` and one `CandidateAllocation` and runs every registered `SchedulingConstraint` (one class per HC-01..HC-12) against it, returning a `ConstraintEvaluation{valid, results, violations}`. It answers exactly one question — "is this specific candidate valid?" — never which candidates exist (Phase 10) or which is best (Phase 11).

**Why one class per hard constraint instead of one giant validation method?** Each constraint is independently unit-testable, independently reviewable, and independently addable — a future HC-13 is a new `@Component`, not a new branch in an ever-growing conditional. It also makes the "evaluate all, don't fail fast" requirement trivial: the engine just iterates a list, it never needs special-case logic to keep going after one check fails, because each check is already isolated.

**Why not one giant validation method?** A single method checking all twelve rules inline would couple unrelated concerns (a change to capacity logic risks breaking software-matching logic in the same function), make targeted unit testing of one rule impossible without exercising all twelve, and make the evaluation order and "did every rule actually run" property much harder to reason about or verify.

**What is the difference between a hard constraint and a soft constraint?** A hard constraint (this phase) makes a candidate invalid — never selectable regardless of score. A soft constraint (Phase 11, docs/07-ALLOCATION-SCORING.md) only ranks among candidates that already passed every hard constraint. `ConstraintResult`/`ConstraintViolation` deliberately carry no score/weight field — mixing the two would let a soft preference silently override a hard rule, exactly what docs/07-ALLOCATION-SCORING.md warns against.

**What is the difference between faculty availability and faculty conflict?** Availability (HC-03) is a static, declared weekly boundary — "can this faculty ever teach Monday 10-11am, per their general schedule?" Conflict (HC-02) depends on real allocation data — "is this faculty already booked for something else at this exact date/time?" A faculty can be generally available at a time they're already booked; verified directly with a test where the identical candidate passes `FacultyAvailabilityConstraint` and fails `FacultyConflictConstraint`.

**Why can A1 and A2 run simultaneously?** Because HC-04 (`BatchConflictConstraint`) only ever compares a candidate against *its own batch's* existing allocations, and HC-05 (`DivisionWideConflictConstraint`) only blocks a BATCH candidate when an overlapping *DIVISION-wide* row exists — a sibling BATCH row is never HC-05's concern either. Two different batches of the same division, with different labs and faculty, therefore pass every applicable hard constraint independently. This is the project's signature scenario and is verified three ways: a dedicated `BatchConflictConstraintTest` case, a dedicated `ConstraintEngineTest` case with all five relevant HC results individually asserted, and a live Docker run against the real seeded BDA/CNS demo data.

**How do you detect interval overlap?** The standard half-open formula, `startA < endB AND startB < endA`, implemented once in `TimeIntervalUtils` (`common` package) and reused by every conflict-related constraint (HC-01, HC-02, HC-04, HC-05) plus, via a Phase 9 `Instant` overload of the same method, HC-06. No constraint reimplements this formula.

**How do you enforce BATCH vs. DIVISION semantics?** The structural invariant (BATCH needs a batch, DIVISION must not have one) is enforced twice already, at the `SchedulingRequest` and `Allocation` construction layers (Phase 8). Phase 9 adds the *cross-candidate* semantics on top: `BatchConflictConstraint` only ever looks at same-batch rows; `DivisionWideConflictConstraint` handles every interaction that involves a DIVISION-type row, in both directions. Splitting these into two constraints (rather than one "batch/division conflict" constraint) keeps each one's logic simple and lets HC-04 stay genuinely one-purpose.

**How do you validate required software?** `RequiredSoftwareConstraint` queries `SubjectSoftwareRequirementRepository` for the subject directly (not from `SchedulingContext` — see below), and checks that every required software code is present in the candidate lab's installed set (`candidate.lab().softwareCodes()`, pre-loaded once per candidate).

**Why use set-subset semantics?** Because HC-08's rule is "the subject needs ALL of its listed software, not just one" — `R_s ⊆ L_ℓ`. A subject requiring both Cloudera and Spark is not satisfied by a lab that only has Cloudera; the missing-items list (`details.missingSoftware`) is exactly `R_s \ L_ℓ`, both for explainability and because computing "what's missing" is cheap once you already have the subset check.

**How do equipment quantities work?** For every `(equipment, requiredQuantity)` row the subject requires, the candidate lab's available quantity (`Map<String,Integer>`, defaulting missing keys to `0` via `getOrDefault` — never a null-pointer risk) must be `>= requiredQuantity`. Shortfalls are collected, not just the first one found, so `details.shortfalls` can report every insufficient item in one violation.

**How do you validate temporary lab unavailability?** `LabAvailabilityConstraint` converts the candidate's `LocalDate`+`LocalTime` interval into an `Instant` range via `SchedulingTimeMapper` (the Phase 8 timezone bridge), then compares it against each `LabUnavailability` row's native `Instant` range using the same half-open overlap formula, generalized to `Instant` rather than reimplemented.

**Why evaluate all hard constraints instead of fail-fast?** Because a candidate can be invalid for several independent reasons at once, and reporting only the first found reason is worse UX and worse debugging — "you can't use this lab: wrong capacity" invites a retry that then discovers "also no Cloudera" on the next attempt. Evaluating everything up front, once, also directly feeds Phase 12 (explainability) and Phase 13 (alternative ranking) without needing a second evaluation pass later.

**Why doesn't a valid candidate automatically create an `Allocation`?** Because Phase 9 is validation only — deciding *which* valid candidate to commit to (when several exist) is a selection/orchestration decision that belongs to whichever workflow calls the engine (Phase 15's extra-lab booking, Phase 19's PDF-import approval), inside its own transaction with its own concurrency handling (Phase 16). Conflating "is this valid" with "persist this" would make the engine impossible to unit-test in isolation and would blur read-only validation with a write path.

**How will Phase 10 use the Constraint Engine?** Phase 10 (Candidate Generation) will build a `CandidateAllocation` for every reasonably-eligible lab (via `CandidateAllocationFactory`, already built) and call `ConstraintEngine.evaluate(...)` once per candidate, keeping only the ones where `evaluation.valid() == true`. The engine itself doesn't change at all for that — its contract ("given one candidate, tell me if it's valid, and why not if it isn't") is exactly what a generation loop needs to call repeatedly.

**Concise algorithm explanation:** *"For a candidate allocation, I build a `SchedulingContext` containing the resolved academic and scheduling data, then a `CandidateAllocation` containing the candidate-specific lab data. The `ConstraintEngine` executes twelve independent `SchedulingConstraint` implementations, one per hard constraint from HC-01 to HC-12. Each returns a structured `ConstraintResult` — pass, fail with a typed violation, or not-applicable for constraints like CR authorization that don't apply to every request. The candidate is valid only if no applicable hard constraint fails. The engine evaluates all twelve regardless of earlier failures, so it can return every reason a candidate is invalid, not just the first one — which is what later phases need for explainability and generating alternatives."*

## Candidate Generation (Phase 10 — implemented, verified answers)

**What is candidate generation?** The layer that turns one `SchedulingRequest` into every relevant `CandidateAllocation` for it - `CandidateGenerator.generate(request)` builds the request's `SchedulingContext` once, then produces one candidate per lab in the system, evaluates each through the real `ConstraintEngine`, and returns a `CandidateGenerationResult` holding all of them, valid and invalid alike.

**How is it different from the constraint engine?** Candidate generation answers "which labs should be considered?" - the constraint engine (Phase 9) answers "is a considered lab valid?" They're deliberately separate classes with separate responsibilities: `CandidateGenerator` contains zero capacity/software/availability logic of its own, and `ConstraintEngine` has no idea how many labs exist or how they were chosen. Neither could silently drift out of sync with the other's decisions, because there's only one place - `ConstraintEngine` - that decides validity at all.

**Why not simply query the first available lab?** Because that's exactly the naive booking system this whole project is built to avoid. Returning the first valid lab would mean the system never actually compares options, never explains why other labs were rejected, and never gives Phase 11 anything to rank. `CandidateGenerator` evaluates every lab every time, with no early return - verified directly: a 16-lab system produces 16 evaluated candidates for one request, not fewer.

**Why do you evaluate invalid labs instead of filtering them all upfront?** Filtering upfront (e.g. skip any lab without the subject's required software before ever constructing a candidate) would mean duplicating HC-08's own logic in a second place, and a lab excluded that way never gets a `ConstraintViolation` attached - there would be nothing to show a CR who asks "why isn't C-304 an option?" Evaluating every lab through the one real constraint engine keeps validity decided in exactly one place and keeps every rejection explainable.

**How are rejected candidates useful?** Each carries its full, structured violation list from Phase 9 (`EvaluatedCandidate.violations()`) - e.g. "C-304: missing CLOUDERA" or "B-201: capacity 50 below required 68." Phase 12 will format these into readable explanations; Phase 13 will use them to understand *why* an alternative is needed and what would need to change. None of that requires re-running generation - the data is already attached.

**Why isn't a valid candidate automatically booked?** Because "valid" here means valid *at generation time*, not booked - candidate generation is read-only and advisory. Selecting which valid candidate to commit to (when several exist) is Phase 11's job once scoring exists; actually persisting that choice safely under concurrent requests is Phase 15/16's job, inside a real write transaction with revalidation immediately before commit. Generation deliberately does none of that.

**How do you avoid rebuilding `SchedulingContext` for every lab?** `SchedulingContextFactory.build(request)` is called exactly once inside `generate(...)`, before the lab loop begins; the resulting `SchedulingContext` is then passed unchanged into every `CandidateAllocationFactory.build(...)` and `ConstraintEngine.evaluate(...)` call. Verified with a dedicated Mockito test asserting the factory is invoked exactly once regardless of how many labs exist.

**How will scoring consume candidate generation?** Phase 11 will call `CandidateGenerationResult.validCandidates()` directly - a plain filtered list of `EvaluatedCandidate`s that already passed every hard constraint - and rank only those. It never needs to touch `invalidCandidates()` for ranking (though Phase 12/13 will, for explanation).

**What happens if there are zero valid labs?** Generation still completes normally and returns a `CandidateGenerationResult` with an empty `validCandidates()` list - never an exception. This is a legitimate scheduling outcome (every lab genuinely fails some constraint for this request), not a technical failure; verified live by temporarily inflating a batch's required strength so every lab failed capacity, and confirming generation still returned a well-formed result.

**How do you prevent stale candidate results from causing double booking later?** By not trying to, in this phase. A candidate marked valid during generation can be taken by another request before any future booking actually commits - candidate generation makes no promise beyond "valid as of this read." The actual safety guarantee belongs to Phase 16: revalidating the real hard constraints again, inside the same transaction as the insert, immediately before commit. Documenting this limitation now (rather than pretending generation is a reservation) is deliberate - see docs/05-SCHEDULING-ENGINE.md.

**Concise algorithm explanation:** *"Given one scheduling request, I build its `SchedulingContext` once. `CandidateGenerator` then obtains every lab in the system and uses `CandidateAllocationFactory` to build a candidate snapshot for each one. Each candidate is passed through the Phase 9 `ConstraintEngine`. The result retains both valid and invalid candidates along with their constraint violations. I deliberately don't return the first valid lab, because Phase 11 needs the complete valid set to rank, and Phase 12/13 need the rejected candidates to explain conflicts and eventually suggest alternatives."*

## Scoring Engine (Phase 11 — implemented, verified answers)

**How does the scoring engine work?** `ScoringEngine.score(generationResult)` reads only `CandidateGenerationResult.validCandidates()` - never the raw candidate list - and runs every Spring-discovered `AllocationScorer` bean against each one, producing a `ScoreContribution` per factor. Those are summed into a `ScoredCandidate{totalScore, maxPossibleScore, contributions}`, and the full set is sorted by normalized score descending, lab code ascending as a deterministic tie-break, into a `ScoringResult`.

**Why are hard constraints separate from scoring?** They answer fundamentally different questions - "is this candidate even legal?" versus "among the legal candidates, which is better?" Collapsing them would let a high soft score somehow excuse a hard failure, which is exactly the bug class this separation exists to prevent. Architecturally this isn't just convention - `ScoringEngine` only ever receives `validCandidates()`, so an invalid candidate is structurally unreachable by any scorer, not merely filtered out by a runtime check that could be forgotten.

**Can a high score override a hard constraint?** No, and this was proven directly: a manual verification scenario built a deliberately adversarial candidate - undersized capacity (invalid, fails HC-07) but matching the subject's preferred lab type (a perfect soft-score candidate otherwise) - and confirmed live that it never appears anywhere in `rankedCandidates()`, regardless of how favorable its soft factors would have been.

**How do you score capacity fit?** `fitRatio = required / labCapacity; score = weight * fitRatio`. Since HC-07 already guarantees every valid candidate has `labCapacity >= required`, the ratio is always in `(0, 1]` - closer to 1 (a tight fit) scores near-full weight, a much larger lab scores materially lower. No rounding-to-zero, no division-by-zero risk, since `required > 0` is a DB-enforced invariant.

**Why don't you simply choose the largest lab?** Because a 150-capacity lab for a 23-strength batch wastes a resource another request might actually need - Capacity Fit specifically rewards *closeness*, not size, so a 25-capacity lab (if it existed and were otherwise valid) would score higher than a 150-capacity one for the same request. This was verified directly: `fitRatio` for capacity 70 against required 68 is far higher than for capacity 150 against the same requirement.

**What happens when a scoring factor is not applicable?** It contributes `ScoreApplicability.NOT_APPLICABLE`, meaning zero points *and* zero to the applicable maximum - not a fabricated full score, not a penalty. `PreferredLabTypeScorer` is the concrete example: a subject with no `preferredLabTypeId` recorded gets this treatment, so it's never unfairly compared against a subject that does express a preference.

**Why isn't the score always out of 100?** Because only three of the six originally-proposed factors turned out to have real, non-fabricated data behind them (Capacity Fit 30, Preferred Lab Type 15, Balanced Utilization 15 - 60 total). Reporting `47/100` when 40 points of criteria don't exist would be dishonest; `ScoringEngine` instead reports `raw/applicableMax` (e.g. `39.58/60.0`) and a separately-computed normalized percentage, and the maximum can differ even between two candidates of the same request if one has `NOT_APPLICABLE` factors the other doesn't.

**Why did you defer faculty preference?** Because no such data exists - `FacultyAvailability` (Phase 7) records *allowed* windows, not *desirable* ones. Treating availability as if it were preference would be inventing a signal from data that was never recorded for that purpose. No `FacultyPreference` table was added just to unlock this factor (see ADR-049) - that would have been manufacturing requirements to hit a target, not honest optimization.

**Why isn't timetable-gap scoring meaningful when every candidate uses the same time?** Because Phase 10's `CandidateGenerator` produces one candidate per *lab* for a single fixed `date`/`startTime`/`endTime` - only the lab varies across candidates in one `CandidateGenerationResult`. A lab choice cannot change how many minutes of gap exist around an existing session, since the time itself never changes within one generation run. This factor only becomes meaningful once Phase 13/14 introduces alternative time slots to actually compare.

**How do you calculate balanced utilization?** `LabUtilizationService` sums each candidate lab's scheduled minutes (REGULAR and EXTRA allocations alike) within the term's currently `PUBLISHED` schedule version, via one grouped SQL query for the whole candidate set. `BalancedUtilizationScorer` then min-max normalizes: `weight * (maxLoad - candidateLoad) / (maxLoad - minLoad)`, or full weight for everyone when every load is equal (including the common all-zero case) - never an absolute percentage, since no working-days/operating-hours concept exists to divide by.

**How do you prevent historical schedule versions from distorting utilization?** By scoping the aggregation query to one explicit `scheduleVersionId` - the term's currently `PUBLISHED` version only, resolved once per scoring run via `ScheduleVersionRepository.findByAcademicTermIdAndStatus(..., PUBLISHED)`. A `SUPERSEDED` version's historical allocations are simply never included in the sum, so an old, no-longer-relevant schedule can't silently inflate a lab's apparent load.

**How are ties handled?** Deterministically - after sorting by normalized score descending, an exact tie is broken by lab code ascending, never left to incidental collection order. Verified live: two labs with identical capacity, identical type, and (for a subject with zero preferences) identical applicable factors produced an exact score tie, and the ranking consistently placed the alphabetically-earlier lab code first.

**Why retain the score breakdown?** Because a bare number can't be explained or trusted - `ScoredCandidate.contributions()` keeps every factor's points/max/explanation/details, so Phase 12 can compose a full user-facing explanation later without re-running any scorer, and so this phase's own manual verification could show *why* C-202 outranked B-201 (preferred-type credit, not just a coincidental total) rather than asserting it opaquely.

**Concise algorithm explanation:** *"Given a `CandidateGenerationResult`, I take only its valid candidates. I load each candidate lab's scheduled minutes once, in one query, then run every registered soft-scoring factor against each valid candidate - Capacity Fit, Preferred Lab Type, Balanced Utilization - summing each factor's points into a total and its max into an applicable maximum. I sort the results by normalized score descending, breaking ties by lab code. Nothing here can promote an invalid candidate, because invalid candidates never reach this stage at all."*

## Explainable Allocation (Phase 12 — implemented, verified answers)

**How does explainable allocation work?** `ExplainableAllocationService.recommend(request)` calls `CandidateGenerator` (Phase 10) then `ScoringEngine` (Phase 11), exactly once each, and converts their already-produced results into one structured `AllocationRecommendation` - the highest-ranked valid candidate becomes the recommendation, every other ranked valid candidate is preserved as an "other valid candidate," and every invalid candidate is preserved with its full rejection reasons. It performs zero additional constraint evaluation and zero additional score computation - it is purely a transformation of results that already exist.

**How do you explain why one lab was chosen over another?** `ScoreComparison.compare(winner, runnerUp)` diffs the two candidates' already-computed `ScoreContribution` lists factor-by-factor, producing a `ContributionDifference` per factor. Verified live: comparing C-202 against B-201 showed `PREFERRED_LAB_TYPE` contributing +15 in C-202's favor while `CAPACITY_FIT` contributed about -4.2 in B-201's favor - a structured, factual answer to "why C-202?", not a vague "it scored higher."

**How do you explain rejected labs?** Every invalid candidate becomes a `RejectedCandidateExplanation` carrying every `ConstraintViolation` it failed (converted to a `ViolationExplanation` with a display label, machine `errorCode` preserved unchanged) - a candidate failing both capacity and software retains both reasons, never collapsed into "not available."

**Why do you preserve invalid candidates?** Because a CR asking "why isn't C-304 an option?" deserves a real, structured answer, not silence - Phase 10 already made this decision (never discarding invalid candidates); Phase 12 is the layer that actually surfaces those preserved reasons to a caller.

**Why don't you just return the highest score?** Because a bare winner with no context is unauditable and untrustworthy - a CR (or an interviewer) needs to see the full ranking, the score breakdown behind it, and why the rejected labs were rejected, to trust that "C-202" wasn't an arbitrary pick. This is also why `otherValidCandidates()` and `rejectedCandidates` are both preserved in full, not discarded once a winner is found.

**How do hard constraints differ from soft-score explanations?** A hard-constraint explanation (`ConstraintCheckExplanation`) reports PASS/FAIL/NOT_APPLICABLE - a binary-ish gate with no notion of degree. A soft-score explanation (`ScoreContribution`, unchanged from Phase 11) reports points awarded out of a maximum - a continuous measure of preference among already-valid options. `RejectedCandidateExplanation` structurally cannot hold a score at all, so this distinction can never be blurred by accident.

**What happens if there is no valid lab?** `status = NO_VALID_CANDIDATE`, `recommendedCandidate = null`, and a factual summary ("N candidates evaluated, N rejected, most common reason: X") - never an exception, never a search for a different time. Verified live by temporarily inflating a batch's required strength so every lab failed capacity.

**Does recommending a lab reserve it?** No. `recommend(...)` runs entirely inside a read-only transaction and creates no row, locks nothing, and reserves nothing. Verified live: the `allocation` table's row count was identical before and after calling `recommend(...)`, including across every scenario run in the same verification session.

**Why is recommendation advisory?** Because a snapshot taken now can be stale the moment another request commits a real booking - concurrent-safe revalidation at commit time is explicitly Phase 16's job, not this one's. Calling the result a "recommendation" rather than a "decision" was a deliberate terminology choice for exactly this reason (see ADR-053).

**How do you avoid recomputing constraints for explanation?** `ConstraintCheckExplanation.from(...)` reads the `ConstraintResult` list already attached to the `EvaluatedCandidate` from Phase 10's `CandidateGenerationResult` - `ConstraintEngine.evaluate(...)` is never called a second time. The one piece of *new* information used (a short reason string for `NOT_APPLICABLE`) is derived from the request's already-known `actor` field, not from re-running HC-11's logic.

**Why is deterministic explainability better than using an LLM?** Because every explanation must be reproducible, auditable, and traceable back to an exact formula or rule - an LLM call would introduce non-determinism, latency, cost, and a layer that could hallucinate a reason unrelated to what the engine actually computed. Every number and reason in an `AllocationRecommendation` is directly attributable to a specific `ConstraintResult` or `ScoreContribution` that already existed before the explanation layer ran.

**How will Phase 13 use rejection reasons?** `RejectedCandidateExplanation.violations()` already tells Phase 13 *why* the originally requested (lab, time) combination didn't work for a given candidate - e.g. "every lab failed `CAPACITY_VIOLATION`" versus "one lab failed only `LAB_UNAVAILABLE`" suggests very different alternative-search strategies. Phase 13 can read this without re-running generation.

## Conflict Analysis + Alternative Suggestions (Phase 13 — implemented, verified answers)

**How does conflict detection work?** `ConflictAnalyzer.analyze(recommendation)` takes an already-computed Phase 12 `AllocationRecommendation` and classifies every rejected candidate's violations as structural or temporal - it never queries the database and never re-runs a constraint. The result, `ConflictAnalysis`, exposes exactly which candidates are "structurally viable" (fail only temporal constraints) and whether alternative-time search is even worth attempting.

**Why don't you implement conflict checks twice?** Because that would create two competing sources of truth about validity. `ConflictAnalyzer` reads only `RejectedCandidateExplanation`/`RejectionSummary` - Phase 12 objects that themselves came from Phase 9's `ConstraintEngine` - and every alternative slot Phase 13 proposes is validated by one more real call to `ExplainableAllocationService.recommend(...)`, the exact same pipeline. There is exactly one place in this entire codebase that decides "is this candidate valid," from Phase 9 through Phase 13.

**How does the system know whether changing time can solve a problem?** By classifying each hard-constraint failure as structural (true at every time of day - capacity, missing software, wrong lab type, academic/authorization facts) or temporal (a lab/faculty/batch/division being occupied, or unavailable, right now - which a different time can genuinely resolve). This is a static lookup table over Phase 9's existing thirteen error codes (docs/06-CONSTRAINTS.md), not a new validity concept.

**What is a structurally viable lab?** A rejected candidate with zero structural failures - it may still fail one or more temporal constraints, but nothing about it is fundamentally wrong for this request. `ConflictAnalysis.structurallyViableLabIds()` is computed directly from already-produced violation lists, with no extra query.

**How do you avoid pointless time searches?** `alternativeTimeSearchWorthwhile()` is simply "at least one candidate is structurally viable." If every rejected candidate has a structural failure (e.g. every lab is too small), no time in the universe can fix that, so the search loop is never entered at all - verified live with `slotsSearched=0` for a genuinely impossible request, and with a dedicated unit test asserting `recommend(...)` was called exactly once (only for the original request).

**How are alternative suggestions ranked?** Lexicographically, never as one merged score: (1) day displacement ascending, (2) time-of-day displacement from the original request ascending, (3) Phase 11's own normalized score descending, (4) lab code ascending as the final deterministic tie-break. A closer, lower-scoring time can and does outrank a farther, higher-scoring one - proven directly with an adversarial fixture (a 20%-score slot 1 hour away beat a 90%-score slot 4 hours away).

**Why prefer same-time alternatives?** Because a different time is more disruptive to a subject/faculty/batch's real schedule than a different lab at the exact same time. In this architecture, "same time, different lab" actually costs nothing extra to check - Phase 10 already evaluates every lab at the requested time as part of building the original recommendation, so if any lab were valid there, the search would already have stopped before ever considering a different time at all.

**How do you prevent alternative-search explosion?** Two independent, configured bounds: at most 6 (day, time) slot combinations are ever run through the full pipeline per search, and at most 3 suggestions are ever returned. `SchedulingSlotProvider` generates its candidate list already sorted and already truncated - no unbounded loop, no "keep searching until found."

**What is the complexity?** `O(min(H*D, maxSlotsSearched) * costOfOneRecommendation)`, where `H` (9 valid start hours/day) and `D` (4 candidate days: same day + 3 lookahead) bound the raw slot count before the configured cap of 6 takes over - a small, fixed multiple of Phase 10/11's own already-documented per-request cost, never combinatorial. No formal benchmark is claimed; only real, informal observations (this document and docs/11-TESTING-STRATEGY.md).

**How are A1/A2 simultaneous sessions handled?** Exactly as Phase 9-12 already established: a real, persisted A1 (BDA) session does not block A2 (CNS) at the same time, because A2 uses a different faculty and a different lab - verified live by persisting a genuine A1 allocation and confirming A2 still receives `ALTERNATIVES_NOT_NEEDED` with its own valid, different-lab recommendation, never a false `DIVISION_CONFLICT`.

**What is the difference between Phase 13 alternatives and Phase 14 backtracking?** Phase 13 searches alternative times/labs for *one* request in isolation, never touching any other already-scheduled session. Phase 14 (not yet built) will consider *multiple* sessions together and may reconsider or move an already-placed tentative assignment while solving a larger schedule. Phase 13 never moves an existing `Allocation` - it only proposes new, independently-valid possibilities.

**Are alternatives guaranteed to remain free?** No - every result here, exactly like Phase 12's recommendation, is a snapshot taken during one read-only transaction. Another request could occupy the same lab/time before any future booking actually commits. Phase 16 owns the real concurrency-safe revalidation at commit time; Phase 13 is advisory decision support only, never a reservation.

**Why doesn't Phase 13 persist allocations?** Because nothing has been decided yet - a suggestion is a possibility, not a booking. Verified live: the `allocation` table's row count was identical before and after every `findAlternatives(...)` call across all required scenarios.

## Automatic Scheduling / Multi-Session Backtracking (Phase 14 — implemented, verified answers)

**Why isn't greedy assignment sufficient for multi-session scheduling?** Because a greedy, fixed-order pass can commit an earlier requirement to a lab that a later, more-constrained requirement needed exclusively - by the time the later requirement is reached, its only option is already taken, and greedy has no mechanism to reconsider the earlier choice. This is proven directly by the flagship test: R1 can use lab X or Y, R2 can use only X; scheduling in fixed order (R1 first) with no backtracking assigns R1→X and then fails R2, even though R1→Y/R2→X is a fully valid schedule.

**What is backtracking, concretely, in this engine?** Depth-first search over requirements: at each node, try each candidate (lab/slot) for the current requirement in a deterministic order, recurse into the remaining requirements with that choice added to the search state, and if every recursive path from that choice fails, undo it (simply don't carry that state forward - `SchedulingSearchState` is immutable, so "undo" costs nothing beyond returning) and try the next candidate.

**Give an example where greedy fails but backtracking succeeds.** Exactly the flagship test scenario: two requirements share one time slot; R1 (fixed order) is tried first and greedily takes lab X, its first workable option; R2 can only use X, so it fails; backtracking then retries R1 with lab Y instead, which frees X for R2, producing a complete schedule. This is asserted directly - `COMPLETE`, `backtracks > 0`, and the final assignment is R1→Y/R2→X, not just "some" complete schedule.

**What is search state, and why is it a new concept here?** `SchedulingSearchState` holds every provisional (not-yet-persisted) decision made so far during one search run - Phase 8-13 never needed this, since every earlier phase evaluated exactly one request against real, already-persisted data. Phase 14 is the first phase where a "candidate" (a provisionally chosen slot for an earlier requirement) must itself be visible to the validation of a later requirement, before either is real.

**How do provisional allocations participate in hard constraint checking?** Through new overloaded methods added alongside the existing Phase 8-12 ones - `SchedulingContextFactory.build(request, searchState)`, `CandidateAllocationFactory.build(context, labId, searchState)`, etc. - that merge `SchedulingSearchState`'s entries (converted to the same `ExistingAllocationSnapshot` shape persisted data already uses) onto the same lists HC-01/02/04/05 already read. The original signatures are untouched and simply delegate with an empty search state, so every pre-Phase-14 caller's behavior is provably unchanged.

**Why not save trial allocations to the database and roll back?** Because a database write, even inside a transaction later rolled back, is visible to any concurrent reader before the rollback happens, and because the brief explicitly required search to never touch the database at all mid-search. `SchedulingSearchState` is a plain in-memory, immutable record - nothing about it can leak outside the current search call.

**How do you prevent double-booking within one generated schedule?** The same way Phase 9 always has - HC-01 (lab conflict) and HC-02 (faculty conflict) reject any candidate overlapping an already-occupied lab/faculty, now additionally seeing the search's own provisional assignments via the mechanism above. No separate "don't double-book within this schedule" logic exists; it's the identical constraint, given a fuller view of what's occupied.

**How does A1/A2 simultaneous scheduling work at this layer?** Exactly as established since Phase 9 - HC-04 only compares a candidate against its own batch's occupancy, and HC-05 only concerns DIVISION-targeted rows; two BATCH requirements for different batches of the same division, with different labs/faculty, pass independently. Verified live: BDA/A1 and CNS/A2 scheduled to the same Monday 09:00 slot in different labs, with `backtracks=0`.

**What is MRV, and why most-constrained-first?** Minimum-Remaining-Values: at each search node, schedule next whichever unassigned requirement currently has the fewest valid choices, recomputed fresh at every node rather than once at the start (a genuine correction to the Phase 1 planning sketch, which assumed a static ordering - see ADR-063). Scheduling the most-constrained requirement first, while the most slack still exists, is exactly what usually lets the search avoid the backtrack the flagship scenario needs when order is fixed - proven directly by a companion test running the identical R1/R2 scenario through the real MRV-enabled path and observing `backtracks == 0`.

**What is the worst-case complexity, and how do you bound it?** Exponential in the number of requirements, worst case - this is a CSP, not claimed to be polynomial. Bounded in practice by a configurable hard node-count limit (`app.scheduling.backtracking.max-nodes`, default 2000); reaching it produces `SEARCH_LIMIT_REACHED` rather than letting the search run unbounded.

**What does `SEARCH_LIMIT_REACHED` mean, and how does it differ from `NO_SOLUTION`?** `SEARCH_LIMIT_REACHED` means the node budget ran out before the search could determine either outcome - "we stopped searching," never "impossible." `NO_SOLUTION` means the full search space was exhausted within budget and zero requirements were ever assignable - a proven negative result. Both are separately, directly tested: a tiny `maxNodes` cutting off a solvable search versus a genuinely infeasible input exhausting an adequate budget.

**How is scoring used without ever overriding a hard constraint?** Exactly as Phase 11 established - `SchedulingChoice` ordering (normalized score descending, then date, then time, then lab code, as separate lexicographic keys, never merged into one number) only ever decides *which order* to try candidates that have already passed every hard constraint. No formula, weight, or score can make an invalid candidate selectable; `computeChoices` only ever receives candidates the real `ConstraintEngine` already validated.

**Why is Phase 14 advisory, with no production API and no persistence?** For the same reason Phase 12/13 were - committing a generated schedule safely under real concurrent writes is Phase 16's problem to solve properly (FCFS/concurrency, ADR-010), and skipping that safety net just to let Phase 14 write directly would undermine the whole point of building it later. Verified live: the `allocation` table's row count is identical before and after every automatic-scheduling run, across every scenario.

**How is Phase 14 different from Phase 13's alternative suggestions?** Phase 13 searches alternative times/labs for *one* request in isolation and never reconsiders any other already-scheduled session. Phase 14 considers *multiple* requirements together and can retry ("backtrack") an earlier requirement's own provisional choice while solving for a later one - the two only share their underlying validation pipeline (`ExplainableAllocationService`/`ConstraintEngine`), never their search logic.

**How is Phase 14 different from Phase 16 concurrency (not yet built)?** Phase 14 solves *which* combination of labs/times satisfies several requirements at once, entirely in memory, against a snapshot of already-persisted data - it never writes anything. Phase 16 will solve *what happens when two real, independent requests try to book the same thing at nearly the same instant* - a database-transaction/locking problem, not a search problem. A schedule Phase 14 produces would still need Phase 16's safe commit path to actually become real allocations.

## Extra Lab Scheduling / CR Booking Workflow (Phase 15 — implemented, verified answers)

**How does a CR book an extra lab?** They call `POST /api/allocations/extra/search` (optional, but the normal flow) to see ranked options, then `POST /api/allocations/extra` naming a subject/batch/date/time/lab. `ExtraLabService` resolves the CR's division and the authoritative faculty server-side, re-runs the real `ConstraintEngine` against the selected lab using current data, and only then persists an `EXTRA` allocation, `PUBLISHED` immediately against the term's currently published `ScheduleVersion`.

**How do you prevent a CR from booking another division's lab session?** `ExtraLabService` never reads `divisionId` from the request at all — it is always resolved from the caller's own `CrAssignment` via `CrOwnershipService`, before anything else happens. Even if a malicious request supplies a real, foreign `batchId`/`subjectId`, faculty resolution fails to find any assignment for that subject under the caller's own division (`404 SUBJECT_FACULTY_ASSIGNMENT_NOT_FOUND`), and if it somehow did resolve, HC-12's own "batch belongs to division" sub-check would reject it (`INVALID_ACADEMIC_RELATIONSHIP`) during book-time evaluation. Verified live: exactly this attack, rejected.

**Why isn't `divisionId` trusted from the frontend?** Because a client-supplied identifier is never authorization — anyone can construct an arbitrary HTTP request with devtools or `curl`, bypassing whatever the real frontend UI would ever produce. The only trustworthy source of "which division can this user act on" is a server-side database lookup against the authenticated user's own id (`CrOwnershipService`), never a value the request itself claims.

**How is faculty selected?** `FacultyAssignmentResolutionService` (Phase 4, unmodified) resolves the authoritative faculty for the subject/division/batch/term combination — exact batch-level assignment first, division-level fallback second, a clear `404` if neither exists. The client never supplies a `facultyId` at all; there is no field for it in either request DTO, so there is nothing to validate against a malicious value — the omission itself is the defense.

**Why do you search first and validate again at booking?** Search is a read-only snapshot of the scheduling pipeline's output at one instant — informative, but not a reservation. Nothing stops another request (or a REGULAR import, or a Lab Assistant edit) from occupying the same lab/time between the search response reaching the CR's browser and the CR clicking "book." Trusting the search result at book time would silently reintroduce exactly the kind of race this project's whole premise is designed to prevent.

**What happens if a lab becomes occupied after search?** Book-time revalidation catches it: `ExtraLabService.book` rebuilds the `SchedulingContext`/`CandidateAllocation` for the selected lab from current data and re-runs the real `ConstraintEngine`, inside the same transaction as the eventual insert. An invalid result produces `409 ALLOCATION_CONFLICT` with the exact structured violation(s) — never a silent success, never a generic error. Proven live: a search recommended a lab, a conflicting allocation was inserted directly, and the subsequent book attempt was correctly rejected.

**Why is transactional revalidation still not sufficient for concurrent requests?** Because "revalidate, then insert, inside one transaction" only guarantees correctness against data that existed *before* that transaction started — it says nothing about a second, truly simultaneous transaction doing the identical check against the identical (still-unmodified) data at nearly the same instant. Depending on isolation level, both transactions can each see the lab as free and each proceed to insert, unless a database-level locking or exclusion mechanism forces one to wait for or fail against the other. Phase 15 deliberately does not claim to have solved this — see the next answer.

**What's the difference between Phase 15 and Phase 16?** Phase 15 makes the booking path *correct against a single request's view of current data* — it eliminates the "stale search" gap. Phase 16 makes it *safe under two simultaneous requests* — a genuinely different, harder guarantee requiring a real database-level mechanism (row locking or an exclusion constraint, ADR-010) and a real concurrent-request test proving exactly one of two racing requests ever succeeds. Phase 15's booking transaction is a necessary building block for Phase 16, not a substitute for it.

**Why use soft cancellation instead of `DELETE`?** Because an EXTRA allocation's history (who booked it, when, why it was later cancelled) is real, audit-relevant data — deleting the row would destroy that history the moment a cancellation happened, contradicting this project's standing "never silently lose scheduling history" principle (the same reasoning behind `ScheduleVersion` superseding rather than deleting, and `CrAssignment` ending rather than deleting). `Allocation.cancel(...)` (Phase 8) already existed for exactly this; Phase 15 is simply the first phase to call it from a real HTTP endpoint.

**How do cancelled allocations stop blocking scheduling?** `AllocationStatus.blocksScheduling()` returns `false` for `CANCELLED` — the single, centralized definition every conflict query (HC-01/02/04/05, via `AllocationQueryService`) already relies on since Phase 8. Cancelling an allocation requires zero new logic to "unblock" the slot; the existing conflict queries simply stop returning that row the moment its status changes. Verified live: the exact same lab/time, re-searched immediately after cancellation, recommended the same lab again.

**How does A1/A2 simultaneous scheduling work in the real booking flow?** Exactly as every phase since 9 has established — HC-04 only compares a candidate against its own batch's occupancy, HC-05 only concerns DIVISION-targeted rows, so two BATCH bookings for different batches with different labs/faculty pass independently. Proven for the first time through the real production endpoint, not just a test fixture: A1/BDA booked into `C-202` and A2/CNS booked into `B-201` at the identical Monday 09:00-11:00 slot, both succeeding via two independent `POST /api/allocations/extra` calls.

**How are hard constraints reused instead of duplicated?** `ExtraLabService` contains no capacity/software/conflict/availability logic of its own anywhere. Search calls `AlternativeSuggestionService.findAlternatives` (Phase 13, unmodified), which itself calls `ExplainableAllocationService.recommend` (Phase 12) → `CandidateGenerator` (Phase 10) → the real `ConstraintEngine` (Phase 9). Booking calls `SchedulingContextFactory.build` + `CandidateAllocationFactory.build` + `ConstraintEngine.evaluate` directly, for exactly one candidate — the same engine, the same twelve constraint classes, zero duplication either way.

**How does the Lab Assistant inspect CR activity?** `GET /api/allocations/extra/activity?academicTermId=...` (LAB_ASSISTANT-only), returning every `EXTRA` allocation for a term with its full audit trail (`createdBy`/`createdAt`/`cancelledBy`/`cancelledAt`/`cancellationReason`, all already on `Allocation` since Phase 8), optionally filtered by division/status. This is deliberately not a full `audit_log` subsystem — that remains a later-phase concern (FR-32/33); Phase 15 exposes exactly the audit data `Allocation` itself already carries, nothing invented ahead of scope.

## FCFS / Concurrency Finalization (Phase 16 — implemented, verified answers)

**Why wasn't Phase 15's transactional revalidation enough?** Because it only guarantees correctness against data that existed *before* that transaction started - it says nothing about a second, genuinely simultaneous transaction reading the identical (still-uncommitted) state at nearly the same instant. Two transactions can each run `ConstraintEngine.evaluate(...)`, each correctly see the lab as free (because neither has committed yet), and each then proceed to insert - both "pass," but only the database's own commit-time behavior determines what actually happens next.

**What is write skew?** A concurrency anomaly where two transactions each read a shared piece of state, each make a decision based on what they read, and each write - and the two writes together violate an invariant that neither transaction's own read-then-decide logic could have caught alone, because each transaction only ever saw a consistent snapshot *before* the other's write. Here: T1 reads "lab free," T2 reads "lab free," T1 writes its booking, T2 writes its booking - both writes succeed, and now the lab is double-booked, even though neither transaction did anything individually wrong by its own local logic.

**How can two transactions both see a lab as free?** Because a normal read (even inside a transaction) doesn't lock anything by default - PostgreSQL's default `READ COMMITTED` isolation lets a `SELECT` see whatever was already committed at query time, with no promise that it will still be true a moment later. Nothing in an ordinary `SELECT ... check for conflicts` step prevents a second transaction from reading the exact same "free" state concurrently.

**How do you prevent double booking?** Two complementary layers, not one: (1) PostgreSQL `EXCLUDE` constraints on `(lab_id, faculty_id, batch_id) × timerange`, which make the database itself reject a conflicting insert at commit time regardless of what any application code believed was true when it started; (2) for the one invariant (DIVISION-vs-BATCH cross-type conflict) that can't be expressed as a single symmetric exclusion constraint, a deterministic per-division pessimistic lock (`SELECT ... FOR UPDATE`) acquired before revalidation, serializing every booking transaction for one division so the existing application-level check can no longer race.

**Why put the final invariant in PostgreSQL rather than trusting the application?** Because application checks can have bugs, a future code path might construct an `Allocation` without going through `ExtraLabService`, and - most fundamentally - multiple backend instances could exist behind a load balancer, each with its own in-process view of "what's currently booked," making any purely in-JVM safeguard structurally unable to coordinate across instances. The database is the one component every instance genuinely shares, so it's the only place a guarantee can be made truly authoritative rather than "probably right, if every code path remembers to check correctly."

**What is an exclusion constraint?** A PostgreSQL constraint type (`EXCLUDE USING <index method> (column WITH operator, ...)`) that generalizes `UNIQUE` from "no two rows may have equal values" to "no two rows may satisfy this operator" - here, `lab_id WITH =` combined with a time range `WITH &&` (overlaps), so the constraint reads "no two active rows for the same lab may have overlapping time ranges." Backed by a GiST index (needing the `btree_gist` extension to combine plain scalar equality with a native range type in one multi-column index), it is enforced by the database at insert/update time, exactly like a unique constraint, but for a genuinely richer "conflicts with" relationship than equality.

**Why use half-open ranges?** `tsrange(start, end, '[)')` matches the exact `[start, end)` convention already used everywhere else time comparisons happen in this project (`TimeIntervalUtils`, `FacultyAvailability`, every hard constraint) - the start instant belongs to the interval, the end instant does not. This makes back-to-back sessions (`09:00-11:00` and `11:00-13:00`) correctly *not* register as overlapping, at the database level, with zero special-casing - verified directly with real inserts before the migration was even written.

**Why not use `synchronized`/`ReentrantLock` in Java?** Because an in-JVM lock only coordinates threads inside one process - it provides zero protection the moment a second backend instance exists (a real, near-certain eventuality for any production deployment behind a load balancer), it doesn't survive a process restart, and it isn't the database enforcing the invariant, so a direct SQL insert (a migration script, a different service, an admin tool) could still violate it. The phase brief explicitly forbids this approach for exactly these reasons.

**How does the design work across multiple app instances?** Trivially - correctly, in fact, without any change at all - because the guarantee lives entirely in PostgreSQL, which every instance shares. Two requests landing on two different backend instances racing for the same lab are protected exactly as if they'd landed on the same instance, since neither instance's own in-process state is what decides the outcome; the shared database is.

**How do you preserve A1/A2 simultaneous scheduling?** Two ways, deliberately: the `ex_allocation_batch_overlap` exclusion constraint is keyed on `batch_id`, so two different batches (A1, A2) never share the key value that would make them conflict, by construction - no amount of concurrency can make this constraint reject them. And the per-division pessimistic lock *serializes* rather than *rejects* - A1 and A2 booking simultaneously both still succeed, just one slightly after the other, each re-validating against current data once it holds the lock. Proven live: concurrent A1/A2 requests both returned `200`.

**Why can't you simply exclude on `division_id`?** Because a plain `division_id WITH =` exclusion constraint would treat *every* pair of overlapping rows in the same division as conflicting - including two different batches (A1 and A2), which must be allowed to coexist. Exclusion constraints compare rows pairwise with the *same* operator on both sides; there's no way to express "conflict only if at least one side is DIVISION-typed" as one symmetric per-row rule without either missing real DIVISION-vs-BATCH conflicts or wrongly rejecting legitimate BATCH-vs-BATCH pairs.

**How do you handle DIVISION vs BATCH concurrency?** Via the per-division pessimistic lock, not an exclusion constraint - `ExtraLabService.book` acquires `SELECT ... FOR UPDATE` on the target division's row before running `ConstraintEngine.evaluate` (which already contains the correct DIVISION-vs-BATCH logic, HC-05, unchanged). Every booking transaction for one division is thereby forced to run one at a time, so the existing query-then-check logic can never observe a stale view of what else is booked in that division. Verified live in both launch-order directions - exactly one winner every time.

**What does FCFS mean in your implementation, precisely?** Among transactions competing for the same exclusive resource/time, the transaction whose insert PostgreSQL actually commits first wins; every other conflicting transaction fails cleanly with `409`. This is deliberately *not* defined as "whichever HTTP request arrived first" - the application has no reliable way to observe true network arrival order across concurrent requests, and claiming otherwise would be an unverifiable promise. Commit order is the only ordering the system can actually prove and enforce.

**What happens to the losing request?** A clean `409 ALLOCATION_CONFLICT`, mapped from whichever of two distinct PostgreSQL/Spring exception shapes actually occurred (an ordinary exclusion-constraint rejection, or - a real behavior found live - a deadlock between two simultaneous inserts each checking the exclusion constraint against the other's uncommitted row) - never a `500`, and never a silent partial success. The response tells the caller which resource conflicted and invites a fresh search, without leaking any raw SQL error text or another user's identity.

**How are database constraint violations mapped to HTTP?** `ExtraLabService.book` wraps the insert in a `try`/`catch` for two Spring DAO exception branches (`DataIntegrityViolationException` for an outright rejection, `ConcurrencyFailureException` for a deadlock), and for each, extracts the violated constraint's name from two independent structured sources - Hibernate's own `ConstraintViolationException.getConstraintName()`, falling back to PostgreSQL's `PSQLException.getServerErrorMessage().getConstraint()` when Hibernate's own extractor can't parse the message shape (a real gap this project found and fixed live, see below) - never by regex-parsing the raw English error text.

**How is cancellation concurrency handled?** Two independent races, each closed differently: cancel-vs-book (a new booking racing an in-flight cancellation of the resource it wants) is handled for free by PostgreSQL's own MVCC behavior - a concurrent INSERT that would conflict with a row currently being UPDATEd by another transaction waits for that transaction to finish, then re-checks against the now-current state, so the outcome is always consistent regardless of which commits first (verified live, repeated 3x, always exactly one active row). Double-cancel (two simultaneous cancel requests for the *same* allocation) needed an explicit fix: `AllocationRepository.findByIdForUpdate` (`PESSIMISTIC_WRITE`) makes the second request block until the first commits, then re-read the now-`CANCELLED` row and correctly fail `INVALID_ALLOCATION_TRANSITION`, rather than blindly overwriting the first cancellation's audit fields. Verified live: exactly one lifecycle transition applied, the loser's own submitted reason never silently persisted.

## Real Engineering Problems Encountered

Real, verified issues only — nothing here is invented. Each entry: symptom, root cause, fix, how it was verified, lesson.

### Problem 1 — `@PreAuthorize` denial returned HTTP 500 instead of 403 (Phase 4)

- **Symptom:** `POST /api/programs` as a `CR` or `STUDENT` user — both correctly denied by `@PreAuthorize("hasRole('LAB_ASSISTANT')")` — returned `500 INTERNAL_ERROR` instead of the expected `403 FORBIDDEN`, discovered via manual `curl` verification against the Dockerized backend, not by any unit test.
- **Root cause:** `@PreAuthorize` denials throw `AuthorizationDeniedException` from deep inside the controller-method AOP proxy, which is still within Spring MVC's own request dispatch. The project's global `@RestControllerAdvice` (`GlobalExceptionHandler`) catches *any* unhandled exception during that dispatch via its generic `@ExceptionHandler(Exception.class)` — including this one — before it could ever propagate out to Spring Security's `ExceptionTranslationFilter`, which only ever sees exceptions that escape the whole dispatch unhandled.
- **Fix:** Added an explicit `@ExceptionHandler({AuthorizationDeniedException.class, AccessDeniedException.class})` to `GlobalExceptionHandler`, mapping directly to `403 FORBIDDEN` in the project's standard error shape.
- **How verified:** Rebuilt the Docker image, redeployed, re-ran the exact same `curl` requests (CR/STUDENT `POST /api/programs`) and confirmed `403 FORBIDDEN` with the correct JSON body.
- **Lesson:** A global `@RestControllerAdvice` and Spring Security's method-security exception handling interact in a way that isn't obvious from either mechanism's documentation alone — the advice sees the exception first. This specifically needs an end-to-end HTTP-level test to catch; a pure method-security unit test (like the removed Phase 3 `RoleAuthorizationTest` fixture) would never exercise `DispatcherServlet`/`@RestControllerAdvice` at all, so it would never have caught this.

### Problem 2 — `LazyInitializationException` with `open-in-view` disabled (Phase 4)

- **Symptom:** `GET /api/cr-assignments/me` (and, latently, several other read endpoints across the academic domain) returned `500` with `org.hibernate.LazyInitializationException: could not initialize proxy - no session`.
- **Root cause:** `spring.jpa.open-in-view: false` (a deliberate Phase 2 setting) closes the Hibernate session as soon as a `@Transactional` method returns. Several service methods returned an entity, and the *controller* (or a DTO factory method called from the controller) then dereferenced a lazy association (e.g. `division.getAcademicYear().getStream().getProgram()`) - by then, outside any transaction, with no session left to fetch it.
- **Fix:** Added class-level `@Transactional(readOnly = true)` to every academic/subject/faculty service (mutating methods already had their own `@Transactional`), so DTO mapping happens while the session is still open. For `CrOwnershipService` specifically, this also required moving the DTO-mapping call *into* the service (`getCurrentAssignmentResponse`), since the controller previously mapped to a DTO after the service call had already returned.
- **How verified:** Same rebuild-redeploy-and-re-`curl` cycle as Problem 1, exercised against every previously-failing endpoint (`/api/cr-assignments/me`, `/api/streams`, `/api/academic-years`, `/api/divisions`, `/api/batches`, `/api/subjects`) plus a fresh CORS/negative-case pass to confirm nothing else regressed.
- **Lesson:** `open-in-view: false` did exactly what it exists to do — it turned a silent, easy-to-miss N+1-prone anti-pattern into a loud, immediate failure during active development rather than a slow, hard-to-diagnose performance problem discovered much later in production. This is the direct, first-hand justification for keeping it disabled (see the interview answer above), and it directly shaped how every Phase 5 lab-domain service was written from the start (class-level `@Transactional(readOnly = true)` applied proactively, not retrofitted after a repeat of this bug).

### Problem 3 — `NullPointerException` in overlap self-exclusion check when updating an availability row (Phase 7)

- **Symptom:** `FacultyAvailabilityServiceTest.createOverlappingExistingIntervalIsRejected` and `createAdjacentIntervalIsAllowed` both threw `NullPointerException` instead of the expected result, caught immediately on the first local unit test run (before ever reaching Docker/manual verification).
- **Root cause:** `rejectOverlap`'s self-exclusion check (used by `update()` so a row doesn't spuriously overlap-reject *itself*) was originally written as `row.getId().equals(excludeId)`. `row.getId()` is always non-null for a real, persisted row (the id is assigned on `save()`), so this is safe in production — but it guarded on the wrong side: `excludeId` is legitimately null during `create()` (there is nothing to exclude yet), and the test's mocked rows hadn't had an id assigned either, so `row.getId()` was null in the test fixture, triggering the NPE the guard should have prevented.
- **Fix:** Changed to `excludeId != null && excludeId.equals(row.getId())` — guards on the value that is legitimately null in the common case (`create()`) rather than the value that should always be non-null once persisted; also hardened the test's `window()` helper to always assign an id, matching how a real repository-returned row behaves.
- **How verified:** Re-ran `./mvnw test` — all 55 unit tests (including both previously-failing `FacultyAvailabilityServiceTest` cases) passed; re-ran the same two scenarios manually against the Dockerized stack (Scenario E: overlap → `409`; Scenario F: adjacent → `200`) with real persisted rows to confirm the fix holds against real data, not just the corrected test fixture.
- **Lesson:** When writing a "the new item vs. everything except itself" comparison, guard on the nullable *exclusion* value, not the entity's own id — inverting that assumption turns a should-never-happen production case into a real crash path, and it's easy to miss if test fixtures don't mirror how persisted entities actually behave (an id assigned by the database, not left null). Caught here by a local unit test before it ever reached integration or manual verification, which is exactly the layer such a defect should be caught at.

### Problem 4 — Catching an expected exception inside a constraint still poisoned the surrounding transaction (Phase 9)

- **Symptom:** The unauthorized-CR manual verification scenario (a `SchedulingRequest` with a CR actor who doesn't own the target division) crashed the entire backend process with `org.springframework.transaction.UnexpectedRollbackException: Transaction silently rolled back because it has been marked as rollback-only` — discovered only during manual Docker verification, since every unit test mocked `CrOwnershipService` and therefore never exercised a real Spring transactional proxy boundary.
- **Root cause:** The first `CrAuthorizationConstraint` called `CrOwnershipService.requireOwnsDivision(...)` and caught its thrown `ApiException` subtypes (`ForbiddenDivisionAccessException`, `ResourceNotFoundException`) to build a structured `ConstraintResult.fail(...)` — consistent-looking with this project's "expected invalidity is a result, not an exception" rule. But `requireOwnsDivision` is itself `@Transactional`; Spring's transaction interceptor marks the *shared, surrounding* transaction rollback-only the instant an unchecked exception crosses that method's own proxy boundary — before the constraint's `catch` block, several stack frames up, ever runs. Catching the exception in ordinary Java code does not "un-mark" a transaction Spring's AOP layer already flagged.
- **Fix:** Switched to `CrOwnershipService.getCurrentAssignment(userId)` — an `Optional`-returning query method that never throws for the "no assignment"/"wrong division" cases — and compared the resolved division directly inside the constraint. No exception crosses any `@Transactional` boundary for this expected-failure path at all now, so there is nothing for Spring to mark rollback-only.
- **How verified:** Rebuilt the Docker image, re-ran the exact same unauthorized-CR scenario against the running stack — the process no longer crashed, and the constraint correctly returned `FAIL`/`CR_ASSIGNMENT_NOT_FOUND` as a normal result. Also updated `CrAuthorizationConstraintTest` to mock the new non-throwing method and re-ran the full local suite (149/149 passing).
- **Lesson:** "Catch the exception and convert it to a result" is not sufficient by itself when the exception originates from inside another `@Transactional`-advised bean method — Spring's transactional AOP marks the transaction rollback-only at the point the exception *leaves that method*, independent of whether a caller further up the stack catches it. The only reliable fix is architectural: never let an expected-failure path cross a `@Transactional` method boundary via an exception in the first place; prefer a query method that returns `Optional`/a sentinel over one that throws, whenever the caller needs to treat "not found" as a normal, recoverable outcome rather than an error. This is invisible to any test that mocks the service — only a real Spring-wired transactional call graph (Docker, or a `@SpringBootTest`) can surface it, which is exactly why manual Docker verification remains part of this project's process even where Testcontainers is blocked.

### Problem 5 — `NullPointerException` building a constraint-violation details map against a provisional allocation (Phase 14)

- **Symptom:** The entire Spring Boot application crashed at startup with `NullPointerException` at `LabConflictConstraint.java:48`, the first time a real provisional lab conflict occurred during a live, multi-requirement automatic-scheduling run (`DevAutomaticSchedulingVerificationRunner`, a temporary `@Profile("dev")` diagnostic). Never caught by any mocked unit test, since every `AutomaticSchedulingEngineTest` mock bypasses the real Phase 9 constraint classes entirely.
- **Root cause:** `PlannedAllocation.toSnapshot()` originally set `allocationId = null` for a provisional (not-yet-persisted) snapshot — a reasonable-seeming choice, since there genuinely is no real database id yet. But `LabConflictConstraint`/`FacultyConflictConstraint`/`BatchConflictConstraint`/`DivisionWideConflictConstraint` (all four Phase 9 conflict constraints, which build their `ConstraintViolation.details()` map identically) call `java.util.Map.of("existingAllocationId", existing.allocationId(), ...)`, and `Map.of` throws `NullPointerException` on any null value. This code path only executes when a real conflict is detected against a provisional entry — never exercised by mocks, and not something any of Phase 9's original tests (all against real, persisted, non-null ids) could have caught, since the provisional-id concept didn't exist until this phase.
- **Fix:** Introduced `PlannedAllocation.PROVISIONAL_ALLOCATION_ID = -1L`, used in `toSnapshot()` in place of `null` — documented as never colliding with a real PostgreSQL `BIGINT` identity value, which always starts at 1 and is positive (docs/ASSUMPTIONS.md A-14). Zero changes required to any of the four tested Phase 9 constraint classes.
- **How verified:** Added `PlannedAllocationTest`, exercising the *real*, unmocked `LabConflictConstraint.evaluate(...)` against a snapshot built via `toSnapshot()`, confirming no exception and a correct `FAIL` result with `details()` containing a well-formed `existingAllocationId`. Reran the full suite (250/250 passing); rebuilt the Docker image and reran the entire 5-scenario manual verification harness, confirming all scenarios now complete cleanly, including the one that previously crashed the process.
- **Lesson:** A field modeled as `null` to mean "doesn't exist yet" is safe only until something downstream assumes non-null — here, four already-tested constraint classes that had never before been asked to describe a violation against data with no real id. A synthetic, always-valid sentinel is often a smaller, more localized fix than teaching every consumer to handle null, especially when (as here) the consumers are stable, already-tested code that shouldn't need to change for a new caller's edge case. This also reinforces why manual, real-pipeline Docker verification stayed part of this project's process even for phases with heavy unit-test coverage — no mock-based test could have exercised the real, unmocked constraint class against a real provisional snapshot the way the live scheduling run did.

### Problem 6 — Hibernate's constraint-name extractor returns `null` for PostgreSQL EXCLUDE-constraint violations (Phase 16)

- **Symptom:** A live, genuinely concurrent cross-division booking race correctly produced exactly one `200` and one `409 ALLOCATION_CONFLICT` (the core guarantee held), but the loser's response carried `"conflictingResource": "resource"` instead of the expected `"lab"` — the constraint-name extraction was silently failing every time, confirmed via a diagnostic debug log printing the full exception cause chain, which showed `org.hibernate.exception.ConstraintViolationException` present in the chain (so the `instanceof` check itself was correct) but with `getConstraintName()` returning `null`, and the exception's own message literally contained the substring `constraint [null]`.
- **Root cause:** Hibernate's PostgreSQL dialect extracts a constraint name by pattern-matching the JDBC error message, and its extractor recognizes the standard unique-constraint phrasing (`"duplicate key value violates unique constraint \"X\""`) but not PostgreSQL's differently-worded exclusion-constraint phrasing (`"conflicting key value violates exclusion constraint \"X\""`) — a different verb ("conflicting" vs. "duplicate") and a different constraint-type name ("exclusion constraint" vs. "unique constraint") that Hibernate's regex simply doesn't match, so it always fails silently and returns `null` for this entire class of violation, not merely in edge cases.
- **Fix:** Added a second, independent extraction source as a fallback: `org.postgresql.util.PSQLException.getServerErrorMessage().getConstraint()` — PostgreSQL's own wire protocol sends the constraint name as a distinct, structured field in every error response (not derived from the message text at all), so this is unaffected by Hibernate's message-shape assumptions. Required widening `org.postgresql:postgresql`'s Maven dependency scope from `runtime` (the Spring Boot starter default) to `compile`, since application code needs to reference the driver's own exception type directly.
- **How verified:** Added a unit test constructing a real `PSQLException` from a hand-built `ServerErrorMessage` wire-format string with a `null`-returning Hibernate `ConstraintViolationException` wrapping it, confirming the fallback resolves the correct resource; rebuilt the Docker image and reran the live cross-division race, confirming `conflictingResource` now correctly reads `"lab"`/`"faculty"`/`"batch"` depending on which constraint fired.
- **Lesson:** A library's own "convenience" extraction method can have blind spots for less-common message shapes it was never tested against — exclusion constraints are a comparatively rare PostgreSQL feature next to plain unique constraints, and Hibernate's extractor was evidently never exercised against one. Preferring a structured, protocol-level field (`ServerErrorMessage.getConstraint()`) over a library's own text-pattern-matched value, whenever the driver actually exposes one, avoids being silently at the mercy of an ORM's specific regex coverage.

### Problem 7 — Genuinely simultaneous conflicting inserts can deadlock during exclusion-constraint checking, not just get rejected (Phase 16)

- **Symptom:** A live, true-parallel cross-division race for the same lab returned an unexpected `500 INTERNAL_ERROR` on the losing request instead of the expected clean `409` — discovered only through real concurrent HTTP requests (`curl` processes launched together via a shell background-and-`wait` pattern), never by any unit test or by sequential "concurrency" tests, since the failure requires the two inserts' internal constraint checks to genuinely overlap in time.
- **Root cause:** When two transactions each insert a new row that overlaps the *other's own not-yet-committed* row (not an already-committed one), PostgreSQL's exclusion-constraint check on each side can end up waiting on the other (similar to how a unique-index insert waits on a concurrently-inserting, not-yet-committed conflicting row) — and when both sides are simultaneously waiting on each other, this is a genuine deadlock cycle, which PostgreSQL's deadlock detector then breaks by aborting one transaction (`SQLSTATE 40P01`, `deadlock detected`, confirmed directly in the Postgres server log: `"Process ... waits for ShareLock on transaction ...; blocked by process ..."`, both directions). This surfaces through Spring as `org.springframework.dao.CannotAcquireLockException` — a completely different exception branch (`ConcurrencyFailureException`) than the `DataIntegrityViolationException` an ordinary "arrives second, sees the already-committed row, gets rejected" exclusion violation produces — so the original `catch (DataIntegrityViolationException e)` block never caught it, and it fell through to the generic `500` handler.
- **Fix:** Added a second `catch (ConcurrencyFailureException e)` block in `ExtraLabService.book`, mapping a deadlock to the identical clean `409 ALLOCATION_CONFLICT` response as an ordinary exclusion-constraint rejection — both mean the same thing to the caller ("this transaction lost the race"), so both produce the same external shape, differing only in an internal log field (`kind=deadlock` vs. `kind=exclusion constraint`). Deliberately no automatic server-side retry was added (a documented decision, ADR-073) — retrying safely would require a cross-transaction retry (the aborted transaction cannot simply continue; PostgreSQL requires a fresh transaction after any error), which needs Spring's self-invocation-avoiding `REQUIRES_NEW`/proxy machinery for a narrow-probability event; a clean `409` inviting the client to resubmit was judged the better-justified, simpler choice.
- **How verified:** Added a unit test forcing `CannotAcquireLockException` from the mocked repository and asserting the identical clean `409` response; rebuilt the Docker image and reran the true-parallel cross-division race 5 times, observing both the ordinary exclusion-violation path and (at least once) the deadlock path, both correctly producing exactly one `200`/one `409`, never a `500`, confirmed directly in the backend's own logs alongside the HTTP responses.
- **Lesson:** "Two concurrent transactions, one wins, one loses cleanly" is not automatically the same code path every time under a database-enforced exclusion constraint — genuinely simultaneous conflicting inserts (not just "one arrives slightly after the other") are a real, distinct failure mode (deadlock) that only manifests under true parallelism, never under sequential or even loosely-overlapping test calls. This is exactly why the phase brief's insistence on *true* concurrent execution (an `ExecutorService`/`CountDownLatch` barrier, or real parallel HTTP requests - never two sequential calls standing in for "concurrency") mattered: a sequential or near-sequential test would never have triggered this path, and the bug would have shipped undetected.
